# K8s 一图速通:从一个 Pod 说起

> 我学一样东西,习惯先问:**它到底解决了什么问题?**
>
> 这篇用"同心圆"的方式讲 K8s —— 从最内圈的容器,**一圈圈往外长,每一圈回答一个问题**。五分钟,走完一整条线。

---

## 第一圈:容器 —— 怎么打包应用

容器解决的问题,用一个程序员老梗就能概括 ——

> **"这程序在我电脑上明明能跑啊!"**

这句话背后,藏着软件交付多年的两个老难题。

**痛点一:环境不一致。**

你的应用在自己电脑上跑得好好的,一部署到测试服务器、生产服务器就报错。为什么?因为操作系统版本、装的库、系统配置…… 哪哪都不一样。**应用和它依赖的环境,被硬生生拆散了。**

**痛点二:隔离和资源,两头难。**

- 直接在一台物理机上跑多个应用?它们的依赖会互相打架,最后只能"一个应用占一台机器",资源严重浪费。
- 用虚拟机(VM)来隔离?问题解决了,但每个虚拟机都得装一整套操作系统,动辄几个 G,启动要几分钟 —— **太重了**。

部署方式就这样一代代进化:

```
  【部署方式的进化】

  物理机时代:一台机器 = 一个应用        (依赖打架,资源浪费)
       ┌──────────────────────┐
       │        App           │
       │   (独占整台机器)      │
       └──────────────────────┘

  虚拟机时代:能隔离了,但太重           (每个 VM 都装整套 OS)
       ┌──────────────────────┐
       │ App  │ App  │ App     │
       │  OS  │  OS  │  OS     │  ← 每个都带一整套操作系统
       └──────────────────────┘

  容器时代:  隔离 + 轻量               (共享内核,秒级启动)
       ┌──────────────────────┐
       │ App  │ App  │ App     │
       │ 容器 │ 容器 │ 容器     │
       ├──────────────────────┤
       │     共享的宿主机内核     │  ← 全机只有一套 OS
       └──────────────────────┘
```

**容器的解法,一招制胜:** 把应用和它需要的全部依赖、环境,打包成一个标准**镜像(image)**。这个镜像不管搬到哪台机器,跑起来都一模一样 —— 而且它**共享宿主机内核**,不用再装一套 OS,MB 级大小、秒级启动,一台机器能塞上百个。

> 一句话:**容器 = 标准化打包 + 轻量隔离,让应用"一次构建,到处运行"。**

**这个"打包"的配方,写在 Dockerfile 里。** 一个最小例子长这样:

```dockerfile
# FROM    基础镜像:在什么环境之上构建(操作系统 + 运行时)
FROM node:18-alpine

# WORKDIR 容器里的工作目录
WORKDIR /app

# COPY    把本机的代码、文件拷进镜像
COPY package.json ./
# RUN     构建时执行的命令(这里装依赖)
RUN npm install
COPY . .

# ENV     环境变量
ENV NODE_ENV=production

# EXPOSE  声明要监听的端口(文档性质,真正映射在启动时指定)
EXPOSE 3000

# CMD     容器启动时默认执行的命令
CMD ["node", "server.js"]
```

一个 Dockerfile 能定义的东西,基本就这些:

| 指令 | 定义了什么 |
|---|---|
| `FROM` | 基础环境(操作系统 + 运行时,如 `node:18`) |
| `WORKDIR` | 容器里的工作目录 |
| `COPY` / `ADD` | 把本机的代码、文件拷进镜像 |
| `RUN` | 构建时执行的命令(装依赖、编译、初始化) |
| `ENV` | 环境变量 |
| `EXPOSE` | 声明要监听的端口 |
| `CMD` / `ENTRYPOINT` | 容器启动时跑什么命令 |

> 换句话说,**Dockerfile = 镜像的配方**:把基础环境、代码、依赖、端口、启动命令一次性固化下来。正因为这套配方可复现,容器才能做到"一次构建,到处运行"。

## 第二圈:Pod —— 怎么把容器跑起来

容器解决了"打包 + 运行"。但当你有几百个容器、几十台机器,新问题就冒出来了:

- 容器崩了,谁把它重启?
- 流量来了,怎么分发到多个容器?
- 谁保证始终有 3 个副本在跑?

这些"大规模协作"的事,容器自己搞不定。**K8s 就是来干这个的。**

而它管理的基本单位,**不是容器,是 Pod** —— 一个比容器更大的盒子:

```
        ┌──────────── Pod(逻辑主机)────────────┐
        │   共享 IP: 10.0.0.5    共享盘: 📁     │
        │   ┌─────────┐    ┌─────────┐          │
        │   │ 容器 A  │    │ 容器 B  │          │
        │   │ (应用) │    │ (日志)  │          │
        │   └─────────┘    └─────────┘          │
        │      ↕ localhost 互通 / 共享文件        │
        └───────────────────────────────────────┘
```

> 一句话:**Pod 是最小的逻辑主机,容器是它上面的进程。** K8s 只认 Pod,不认裸容器 —— 哪怕一个 Pod 里只有一个容器,也得包进 Pod 里。

## 第三圈:运行与配置 —— 怎么管 Pod、怎么喂它

Pod 能跑了,但生产环境还会抛出两类问题:**怎么管它的生死和发版?** 和 **它的配置、数据从哪来?** 这一圈把 Deployment、ReplicaSet、ConfigMap、Secret、PV/PVC 一起说清。

### 管生死发版:Deployment + ReplicaSet

一旦上生产,两个问题立刻绕不开:

1. **发新版本,怎么不停机、出问题还能回退?**
2. **某个 Pod 突然挂了,业务会不会断?**

K8s 用 **Deployment**(底下挂着 ReplicaSet)一起解决。逐个看。

**问题一:新版本怎么发布?**

最朴素的做法是停掉旧 Pod、启动新 Pod —— 但这样会有一段服务中断,而且新版万一有问题,已经回不去了。

Deployment 给你两件武器:

| 能力 | 怎么做 |
|---|---|
| **滚动更新** | 新版 Pod 一个一个地换,全程始终有副本在跑,**零停机** |
| **回滚** | 新版炸了?`kubectl rollout undo` 一键退回上个版本 |

**滚动更新到底怎么发生?** 看旧版 `3→0`、新版 `0→3` 的全过程 —— 两者此消彼长,中间始终有副本在服务:

```
   滚动更新:旧版一个个退,新版一个个进

   起点   v1 [Pod][Pod][Pod]      v2 (空)                  ← 3 个旧版
   ①      v1 [Pod][Pod][Pod]      v2 [Pod✨]                ← 先拉起 1 个新版
   ②      v1 [Pod][Pod]           v2 [Pod✨][Pod✨]          ← 干掉 1 个旧版
   ③      v1 [Pod]                v2 [Pod✨][Pod✨][Pod✨]     ← 新版到 3
   ④      v1 (空)                 v2 [Pod✨][Pod✨][Pod✨]     ← 旧版清零 ✅

   ↑ 全程可用副本 ≥ 3,用户毫无感知 —— 这就是"零停机"
```

> 节奏由两个旋钮控制:`maxSurge`(最多能**多**起几个,默认 25%)和 `maxUnavailable`(最多能**少**几个,默认 25%)。想更稳就调小、想更快就调大。

而这一切的底层机制是:**每发一个版本,Deployment 就新建一个 ReplicaSet**(新版的),慢慢把它扩到目标数,同时把旧的缩到 0 —— **但旧的不删,留着当"后悔药"**:

```
   Deployment(管版本历史)
     ├── ReplicaSet v2(新版) → [Pod✨][Pod✨][Pod✨]   ← 扩到 3
     └── ReplicaSet v1(旧版) → 保留(缩到 0,可随时回滚)
```

**FAQ:那能回滚到更早的版本吗?比如都发到 v3 了,还能退回 v1?**

能 —— 只要 v1 的 ReplicaSet 还在"保质期"内。发到 v3 时,Deployment 里其实存着 3 个 ReplicaSet:

```
Deployment
 ├── ReplicaSet (v3) → [Pod✨][Pod✨][Pod✨]   活着
 ├── ReplicaSet (v2) → (0)                    保留,缩到 0
 └── ReplicaSet (v1) → (0)                    保留,缩到 0  ← 还能回这
```

v1、v2 的 ReplicaSet 都没删(只是缩到 0),所以你能直接跳回去:

```bash
kubectl rollout undo deployment/xxx --to-revision=1   # 跳回 v1
kubectl rollout history deployment/xxx                # 先看有哪些版本可选
```

(不带 `--to-revision` 只会退到**上一个**版本。)

**但"后悔药"有保质期:** Deployment 默认只保留 **10** 个历史版本(`revisionHistoryLimit: 10`),更老的 ReplicaSet 会被自动清理。所以——

| 情况 | 能回 v1 吗 |
|---|---|
| 才发到 v3 | ✅ 能,ReplicaSet 还在 |
| 已经发到 v15 | ❌ v1 早被清理了,只能重新部署那个镜像 |

> 一句话:**回滚不只是退一步,`--to-revision` 能跳好几步 —— 但药有保质期,超过 10 个版本就过期了。**
>
> 小细节:回滚到 v1 时,其实是用 v1 的镜像**新建一个 ReplicaSet**(分配新的版本号),而不是"复活"原来的 —— 这样版本号永远只前进、可追溯。

**问题二:Pod 突然挂了,业务会不会断?**

不会 —— **因为有人盯着,挂了立刻补。**

干这事的是 **ReplicaSet**。你声明"我要 3 个",它就死循环地盯着实际数量:

```
   ReplicaSet "我要 3 个"
        ↓
   [Pod] [Pod] [Pod]   ← 突然死掉 1 个
        ↓ 控制器立刻补上
   [Pod] [Pod] [Pod✨]
```

少了就补、多了就删 —— 这就是 **控制循环**,也是 K8s 的灵魂(**声明式**:你只说"要什么",它自己把实际拉向期望)。节点宕机也好、Pod 崩溃也罢,ReplicaSet 都会自动把副本数拉回来。这就是所谓的"**自愈**"。

> 小结:**ReplicaSet 管"保活",Deployment 管"发版"。** Deployment 坐在 ReplicaSet 之上,每次发版新建一个 ReplicaSet。所以你日常写的几乎都是 Deployment,ReplicaSet 只是它内部的零件。

### 喂配置数据:ConfigMap / Secret / PV / PVC

Pod 能跑、能维护了,但它的**配置和数据从哪来?** 还差两块:

- **配置 / 密码** → 用 **ConfigMap / Secret**(把配置从镜像里剥出来,改配置不用重打镜像)
- **持久化数据** → 用 **PV / PVC**(Pod 死了,数据还在)

**但 ConfigMap 有两个硬伤,得知道:**

**① 改了配置,正在跑的 Pod 不一定能"热更新"**

- 用**环境变量**注入的配置:Pod 启动时就固定了,**改 ConfigMap 不会生效**,必须重启 Pod。
- 用**挂载文件**注入的:kubelet 会把新文件同步进容器,但**应用通常只在启动时读一次配置**,文件变了它也不知道。

结果:改完 ConfigMap,常见做法是手动 `kubectl rollout restart` 滚动重启。**本质是"重启才生效"的静态配置,不是真正的动态配置。**

**② ConfigMap "重"在哪**

- **大小硬限 1 MiB**(etcd 的限制),超大配置得拆分。
- 每次改动都要 `kubectl apply` → API server → etcd,是一笔 K8s 资源变更,**不适合高频动态配置**(比如经常变的限流阈值、功能开关)。

| 配置场景 | 推荐 |
|---|---|
| 启动时读、很少变 | **ConfigMap**(够用) |
| 配置变了想让 Pod 自动重启 | **Reloader**(监听 ConfigMap,自动触发 rollout) |
| 经常变、需要推送式热更新 | **配置中心**(主流:**Nacos**) |

**中间档 Reloader:配置一变,自动滚动重启。** 它不直接重启 Pod,而是往 Deployment 的 Pod 模板里塞一个注解(配置的 hash),**触发 K8s 自己的滚动更新机制**(就是前面讲的那套)去重建 Pod —— 零停机、应用不用改一行代码。但本质还是"重启生效",不是真热更新。

> 顺带一提:这种"配置变了自动重启"的能力,云厂商的托管 K8s 往往**内置**了,比如**腾讯云 TKE** 就自带,不用再单独装 Reloader。

**真要动态配置,Java 生态的主流选择是 Nacos。** Nacos(阿里开源,名字来自 **Na**ming + **Co**nfig)正好补上 ConfigMap 的缺口:

- **推送式热更新** —— 你在 Nacos 改配置,它**主动推给应用**,应用监听到变化自动重载,**不用重启 Pod**。
- **版本管理 + 回滚** —— 每次改动都有历史记录,配置也能一键回滚(跟 Deployment 回滚一个思路)。
- **多环境隔离** —— 用 namespace 切 dev / test / prod。
- **配置灰度** —— 按机器 IP / 分组,只把新配置推给一部分实例先试水。

> 顺带一提:Nacos 不只是配置中心,**它还是服务注册中心(服务发现)** —— 在 Java 微服务里同时干了 Consul 的活。很多 Spring Cloud / Dubbo 项目里,Nacos 一个顶俩。
>
> 所以在 K8s 里跑 Spring Cloud 应用,常见是**两套并存**:K8s Service 管"网络入口",Nacos 管"应用层的服务注册 + 动态配置",各管一段。

> 一句话:**镜像管程序,ConfigMap 管配置,PVC 管数据 —— 三者解耦。** 但 ConfigMap 是"重启才生效"的静态配置,真要动态热更新,就上 Nacos 这类配置中心。

## 第四圈:网络可达 —— 怎么被访问

Pod 能跑、能维护、有配置有数据了。但还有个根本问题:**它怎么被访问?** 分两种:**集群内部互调** 和 **外部用户进来**。

### 对内:Service —— 服务间调用的门牌号

微服务架构下,服务之间是**互相调用**的:订单服务要调用户服务,用户服务要调商品服务…… 这种**内部的服务间调用**是日常。

但有个麻烦:**被调用的那个服务,它的 Pod IP 一直在变** —— 每次重建、扩缩容,IP 就换。调用方根本没法写死一个 IP 去连它:

```
   订单服务 ──调用──>  用户服务 ???
                         ↑ Pod IP 一直漂移,到底连哪个?
```

于是有了 **Service**:它给一组 Pod 一个**稳定不变的调用地址**。调用方只认这个地址,背后 Pod 随便换:

```
   订单服务 ──>  Service(固定 IP + DNS 名:user-service)
                     │  自动负载均衡
                     ↓
                [Pod]  [Pod]  [Pod]   ← 这几个 Pod 怎么变都不影响
```

实际开发中你根本不用记 IP,直接用 **DNS 名**调用,既好记又稳定:

```bash
http://user-service                                  # 同命名空间,直接用名字
http://user-service.default.svc.cluster.local        # 跨命名空间的完整写法
```

> 一句话:**Service 是内部服务间调用的基石** —— 给会漂移的 Pod 们钉上一个固定门牌号(IP + DNS 名),还顺带把流量负载均衡到多个副本。**Pod 是会跑的人,Service 是不变的门牌号。**

### 对外:Ingress —— 集群的总机台

Service 默认只对**集群内部**开放(ClusterIP)。那外面的人怎么访问进来?

**痛点**:你有 10 个微服务要让互联网用户访问 —— 每个都用 LoadBalancer 暴露,就是 10 个云负载均衡器、10 个公网 IP,贵死 💰;用 NodePort 又是一堆丑端口、还没法按域名分流。你想要的是**一个统一入口**,按域名/路径分发到不同服务 —— 这就是 Ingress。

```
                    互联网用户
                       │
                       ▼
          ┌──────────────────────────────┐
          │   Ingress(一张路由表)         │  ← 统一入口
          │   api.foo.com        → Svc A │   按域名
          │   api.foo.com/users  → Svc B │   按路径
          │   admin.foo.com      → Svc C │
          └──────────────────────────────┘
              │        │        │
              ▼        ▼        ▼
           Svc A    Svc B    Svc C → 各自的 Pod
```

**关键认知:Ingress 资源 ≠ Ingress Controller。** Ingress(资源)只是一张路由规则的声明(纯 YAML),本身不干活;真正接收流量、转发的是 **Ingress Controller**(nginx-ingress / Traefik / ALB…)。没有 Controller,规则就是废纸。

它和 Service **不是取代关系,而是前后关系**:

```
   外部流量 → Ingress Controller →(按规则)→ Service → Pod
```

Ingress 管 **L7 路由**(域名/路径),Service 管 **L4 负载均衡**到 Pod —— 一个管路由、一个管负载,分工合作。顺带,Ingress 还能**统一管 HTTPS 证书**(TLS 在它这儿卸载)。

### 延伸:什么时候需要 Service Mesh?

到这里,Service + Ingress 基本够用了。但有两个常见需求,它们搞不定,得在 Service 之上再盖一层 **Service Mesh**(代表:Istio、Consul)。

**① 灰度发布:想精确控制流量比例**

滚动更新时,流量是**按 Pod 数量**分的 —— 2 个旧 Pod + 1 个新 Pod,新版会自动拿到约 1/3 的流量:

```
   Service ──> [v1旧][v1旧][v2新]   ← 各拿 1/3,新版自动 ~33%
                                    想只给新版 1% 做灰度?做不到(除非堆 99 个旧 Pod)
```

Service Mesh 把流量分配从"按数量"改成"**按权重**",和 Pod 数无关 —— 同样 3 个 Pod,也能切成 99 : 1,新版只拿 1%。这才是真正的灰度 / 金丝雀发布。

**② 跨集群调用**

K8s Service 只管**单个集群**。集群 A 的服务要调集群 B 的服务,Service 管不到。Service Mesh 能把多个集群打通,还顺带加上 mTLS 加密。

```
   ┌── Service Mesh(Istio / Consul)──┐   按权重切流量 · 跨集群 · mTLS · 可观测
   └──────── 建立在 ── K8s Service ───┘   稳定 IP + DNS + 四层负载(地基)
```

> 一句话:**K8s Service 是地基;一旦你需要"按比例切流量"或"跨集群",就得加 Service Mesh。**
>
> 小趋势:简单的灰度 / 对外路由,现在 K8s 原生的 **Gateway API** 也能做,不一定非得上整套 Istio。

## 第五圈:Namespace —— 怎么分区管理

最后一圈不是给 Pod 加能力,而是给整个集群**划区**。

**痛点**:一个集群好几个团队或环境共用 → 名字打架、互相踩、抢资源、没法控权。Namespace 把一个物理集群切成多个"逻辑虚拟集群":

```
   一个集群
   ┌───────────┬───────────┬───────────┐
   │  team-a   │  team-b   │   prod    │
   │ frontend  │ frontend  │ frontend  │  ← 同名也不冲突
   │ 配额 10G  │ 配额 10G  │ 配额 50G  │  ← 各有预算
   │ 门禁:只A │ 门禁:只B │ 门禁:运维 │  ← 各有权限
   └───────────┴───────────┴───────────┘
```

| 解决的问题 | 靠什么 |
|---|---|
| 名字冲突 | 每个 Namespace 内名字独立,可重名 |
| 抢资源 | **ResourceQuota** 限 CPU / 内存 / 对象数 |
| 控权 | **RBAC** 按空间授权 |
| 分组管理 | 按团队 / 环境 / 项目 |

**⚠️ 最大误区:Namespace 默认不是网络隔离。** 不同 Namespace 的服务默认**网络是通的**,跨空间访问用全名 `frontend.team-b.svc.cluster.local`。它是**管理边界**(名字 / 配额 / 权限),不是安全边界 —— 要网络隔离得加 NetworkPolicy,要硬隔离得上独立集群。

> 一句话:**Namespace 是集群里的"楼层划分"** —— 解决命名、配额、权限的软隔离;但默认不管网络(要 NetworkPolicy),要硬隔离得上独立集群。

---

## 一图速通

把五圈收束到一张图,这就是整篇文章的终点 —— 每一圈回答一个问题,层层往外:

```
  【K8s 同心圆:每一圈回答一个问题】

  第五圈 ── Namespace                                怎么分区管理(命名/配额/权限)
  第四圈 ── Service + Ingress                        怎么被访问(对内 + 对外)
  第三圈 ── Deployment/RS + ConfigMap/Secret/PV/PVC  怎么管、怎么喂
  第二圈 ── Pod                                      怎么跑(最小逻辑主机) ⭐
  第一圈 ── 容器                                     怎么打包(标准化镜像)
```

真正高频用的,是这条贯穿五圈的核心链路:

```
  ⭐ 必记五件套(掌握它 = 拿下 80% 日常):

  Pod → Deployment → Service → ConfigMap/Secret → PV/PVC
```

翻译成人话:**把应用(Pod)用 Deployment 管起来,用 ConfigMap/Secret 塞配置、PV/PVC 存数据,用 Service 对内互调、Ingress 对外暴露。**

## 结尾

回头看这五圈,逻辑特别清楚 —— 每一圈都在回答上一圈留下的新问题:

> - **容器**:怎么把应用打包,到处运行?
> - **Pod**:怎么让容器共享环境、被整体调度?
> - **运行与配置**:怎么管 Pod 的生死发版,怎么喂它配置和数据?
> - **网络可达**:怎么让 Pod 被访问(对内 Service、对外 Ingress)?
> - **Namespace**:一个集群多人共用,怎么分区管?

记住这条"问题驱动的同心圆",你就速通了 K8s。
