# 卡片一：IDSvc 连接池碎片化引发 FD 堆积

## 一、30 秒电梯版（面试官只想听结论时用）

> "我们线上一个鉴权相关的服务（IDSvc），进程的文件描述符数一直在慢慢往上涨，没有明显的下降点。排查下来发现是两个问题叠加：一是它调用下游服务时，每次都新建一个 client，导致连接池没法跨请求复用，连接越攒越多；二是它自己作为 HTTP server，没有配置空闲连接的超时时间，客户端连上来之后哪怕不用了，服务端也不会主动关。最后的修复就是两件事：出站请求统一复用一个共享的 Transport，入站 server 加上 IdleTimeout 和 ReadTimeout。上线后 FD 数就稳定了。"

如果面试官追一句"这个故事你想表达什么"，可以直接说：**"资源池类故障的核心，往往不是某个复杂算法出了 bug，而是"这个资源到底该不该被复用、该不该被回收"这个基本问题没人管。"**

---

## 二、完整版（面试官想听细节时展开）

### 1. 背景：怎么发现的

> "这个服务叫 IDSvc，是走 Keycloak 做身份认证相关的一个内部服务。当时不是业务报错发现的，是运维在看服务容器的资源指标时，注意到这个服务的 FD（文件描述符）数量一直在缓慢增长，压测或者流量高峰之后也不会掉回来。FD 涨得多了之后，容器可能会碰到 too many open files 的风险，所以这个当时被当成一个隐患去排查，而不是等它真正炸了才处理。"

### 2. 排查过程：怎么一步步定位到的

> "第一步是把 FD 分类看，到底是 socket 占的多，还是普通文件占的多——发现绝大部分是 TCP 连接，也就是网络连接堆积，不是文件泄漏。
>
> 第二步是把连接按方向拆开看：一部分是这个服务作为客户端，去调用下游 IDSvc 接口时建的连接；另一部分是别的服务作为客户端连过来的入站连接。这两部分要分开看，因为根因完全不一样。
>
> 出站这边，往代码里看，发现每次要调用 Keycloak/IDSvc 相关接口时，都会走一个 `NewClient()`，这个方法每次都会 new 一个新的 `gocloak.GoCloak` 客户端，而这个客户端默认自己带一套 HTTP Transport、也就是自己的连接池。问题就在这——高频调用的话，等于每次都在开一个新的连接池，彼此互不复用，之前建的连接不会被后面的调用捡回来用，只能等各自的 idle timeout 才回收。当时给的一个粗估是：50 QPS、90 秒空闲超时的情况下，堆出来的 ESTABLISHED 连接能到四千多条。
>
> 入站这边，看这个服务本身是怎么启动 HTTP server 的，发现是直接用 Gin 的 `Engine.Run()` 起的，底层其实就是标准库 `http.Server` 的默认配置，没有单独设 `IdleTimeout`。也就是说，客户端跟它建立了 keep-alive 连接之后，只要客户端不主动断，这个连接服务端会一直占着，不会主动清。"

### 3. 根因：一句话总结

> "本质上是两类'该复用/该回收的资源没人管'：一个是客户端每次都新建连接池，导致连接没法跨请求复用；一个是服务端没有空闲连接超时，导致挂着不用的连接也不会被清理。两个问题叠加，FD 数就只涨不跌。"

### 4. 解决方案：具体怎么改的

> "出站那部分，本质就是一句话：**把"每次调用各自持有一个连接池"，改成"所有调用复用同一个连接池"**。代码上落地是一行：让每次 `NewClient()` 出来的客户端都复用同一个进程级的共享 Transport——`RestyClient().SetTransport(chttp.SharedTransport())`。这个共享 Transport 本身配了 `MaxIdleConns: 200`、`MaxIdleConnsPerHost: 50`、`IdleConnTimeout: 90s`，相当于把连接池收敛成一个受控的整体，而不是随着调用次数无限碎片化。没有引入新机制，就是把本该复用的东西真正复用起来。
>
> 入站那部分，把 `Engine.Run()` 换成显式的 `http.Server`，加上 `IdleTimeout: 60s` 和 `ReadTimeout: 30s`。60 秒空闲就主动关连接，30 秒读超时防止慢请求或者异常连接把连接和 goroutine 长期占着。"

### 5. 效果与复盘

> "上线之后跟踪了一段时间，FD 数在压测之后能稳定收敛，不再是单边往上涨的曲线。复盘下来我自己的一个收获是：这种连接池碎片化的问题很隐蔽，代码逻辑本身是对的，接口调用也不会报错，只有把 FD/连接数这类底层资源指标摆到面前，才会意识到问题。所以现在看到'每次调用都 new 一个 client'这种写法，我会本能地多问一句：这个 client 内部是不是自己带了连接池？这个连接池是不是该被复用？"

## 三、面试官可能的追问 + 参考答法

**Q1：你怎么确定是连接池的问题，而不是别的原因（比如 goroutine 泄漏）？**
> "先分类：FD 里 socket 占比很高，基本排除了普通文件泄漏；再看这些 socket 的状态，主要是 ESTABLISHED 而不是 CLOSE_WAIT/TIME_WAIT，说明连接是"活着但没人管"，不是关闭流程有问题。再结合调用量和 QPS 做个粗算，量级对得上，才敢下这个结论，不是猜的。"

**展开：如果占多数的不是 ESTABLISHED，会指向什么方向？**（面试官追问"那你怎么区分不同的连接问题"时可以展开讲，这套方法比只看 FD 总数更有诊断力——总数只能告诉你"有问题"，状态分布能告诉你"该往哪查"）

| 主导状态 | 通常指向的问题 | 典型场景 |
| --- | --- | --- |
| **ESTABLISHED** 持续偏高、不随流量回落 | 连接建立了，但没被跨请求复用，也没有 idle timeout 回收——池子碎片化 | IDSvc 这次的情况 |
| **CLOSE_WAIT** 大量堆积 | 对端已经发了 FIN，本端代码却没调用 `close()`——本质是应用层连接没有正确关闭 | 常见于处理响应时某个分支提前 `return`，没走到 `resp.Body.Close()`；或者异常路径没进 `defer` |
| **TIME_WAIT** 大量堆积 | 主动关闭连接的一方太多太快，短连接模式下频繁开关，四次握手后要等 2MSL 才释放 | 短连接高频调用；或者连接池被批量驱逐重建瞬间产生大量关闭（详见**卡片二**） |
| **SYN_SENT** 大量堆积 | 连接发出去了但没建立成功，通常是下游没响应 | 下游服务过载、accept 队列满，或者网络分区/防火墙拦截 |
| **LISTEN** 出现重复/异常 | 一般不该堆积，如果同一端口反复出现，可能是端口没被正确释放 | 少见，通常是服务重启/优雅关闭逻辑有问题 |

区分 CLOSE_WAIT 和 TIME_WAIT 是最容易被追问的一个点，一句话记住：**"CLOSE_WAIT 是我该关但没关；TIME_WAIT 是我关了但要等"**——前者是自己代码的 bug，后者往往是设计模式（短连接/批量重建）导致的正常但过量的现象。TIME_WAIT 的完整机制和治理方式单独展开成了**卡片二**。

**再追一层：光看 `ss`/`netstat` 的状态字段，能不能判断连接是不是"空闲"的？**
> "不能，这是个要老实承认的局限。`ss` 给的只是某个时间点的状态快照——ESTABLISHED 只说明 TCP 层面这条连接还没断，不说明它当下是在传数据还是已经挂了很久没人用，纯看状态字段区分不出来。
>
> 真正判断'是不是空闲堆积'，是几种信号一起佐证的：一是看趋势而不是单点，把连接数曲线和 QPS 曲线放一起看，QPS 平稳但连接数一直涨，就说明这些连接没有被复用去承载新流量，是攒下来的；二是 `ss -o` 能看到 keepalive 定时器信息，侧面推测多久没包经过，但这是近似值，而且依赖开了 TCP keepalive；三是 `conntrack -L` 里每条连接的 timeout 倒计时，接近默认上限说明很久没包经过，比 `ss` 更接近真实空闲状态；最后也是最关键的一环——反过来用代码印证，找到 `NewClient()` 每次新建 Transport 这个 bug 之后，'为什么会堆这么多 ESTABLISHED'就有了解释，再拿 QPS × idle timeout 估算出的量级去对实际观察到的连接数，两边对得上才真正下结论，不是单靠 `ss` 的某个字段直接看出来的。"

**Q2：为什么"每次 new client"会有问题？直觉上不应该每次调用完就该被回收吗？**
> "客户端本身可能没被回收，但它内部持有的 HTTP Transport / 连接池是异步维护的——即使外层的 client 对象被 GC，底层已经建立的 TCP 连接，只要没到 idle timeout，Go 的 Transport 不会主动关。而且更关键的是：如果每次都新建 Transport，就没有'跨请求复用连接'这件事了，等于每次调用都在浪费一次三次握手的成本，同时占着一个连接位。"

**Q3：这两个修复（复用 Transport / server 加 IdleTimeout）有没有风险？**
> "有。第一个风险是共享 Transport 之后，如果某个下游接口异常卡住，会不会通过共享连接池影响到别的调用——这个要看 Transport 本身的隔离粒度（比如按 host 限制 `MaxIdleConnsPerHost`），以及有没有配超时和重试。第二个风险是 server 端加了 30 秒读超时之后，要确认业务里是不是真的没有合法的、超过 30 秒的慢请求，否则会误杀正常请求，这个当时是做了排查确认的。"

**Q4：这种问题怎么提前发现，而不是等 FD 涨上去了才排查？**
> "关键是要有连接池/资源池本身的可观测性，而不是只监控最终结果（FD 数、内存）。比如 Go 的 http.Transport 复用率、建连次数这些指标，如果平时就能看到，问题会在'刚开始碎片化'的阶段就被发现，而不是等 FD 已经涨到几千才反应过来。"

**Q5：你还遇到过类似的资源池问题吗？（顺势带出线程池案例）**
> "有，性质很像，但发生在 Java 线程池上。当时是一个可重入的异步任务，因为前端 bug 被同一个租户反复触发，量放大了几十倍，而这个任务又慢（3-5 分钟一次），跟主业务共用同一个线程池，最后线程池被这些慢任务占满，正常请求拿不到线程，核心业务直接不可用了。
>
> 根因跟 IDSvc 那次其实是同一个模式：**该隔离的没隔离**（旁路任务和主链路共用一个池）、**该有界的没真正有界**（用了无界队列，导致 `maximumPoolSize` 从来没被触发过）。修复也是对应的两件事：给旁路任务拆一个独立线程池，队列换成有界的，再加上任务级别的幂等去重。
>
> 我自己的体会是：不管是线程池还是连接池，出故障基本都能落到几个问题上——这个资源该不该被共享、上限是不是真的有效、空闲的时候会不会被回收、出问题之前有没有指标能看见。这两次踩的坑正好一个是连接池、一个是线程池，但排查的思路是一套。"

# 卡片二：MySQL 连接池 idle 容量太小导致 TIME_WAIT 端口耗尽

> 对应真实提交：`b2cd459333c`——fix(idsvc): 修复高并发下 MySQL 连接驱逐导致 TIME_WAIT 端口耗尽问题（Issue #73978 / PR #89818）。这是真实的代码改动，可以像卡片一那样当亲历故事讲。

## 一、30 秒电梯版

> "还是 IDSvc 这个服务，但这次是它自己的 MySQL 连接池出的问题。高并发下会突发性地出现连接失败，报错是本地端口分配不出来。排查下来发现根因很反直觉：连接池配的 `MaxOpenConns`（最多能开的连接数）是 200，但 `MaxIdleConns`（能留着复用的空闲连接数）默认只有 100——两个数字不匹配。高并发的时候，同时在用的连接经常超过 100，用完还回池子的时候，空闲槽位已经满了，Go 的连接池会把多出来的连接**直接物理关闭**，而不是留着复用。关得多了，同一个时间窗口里产生大量主动关闭，就堆出一大批 TIME_WAIT，把本地临时端口占满了。修复就是把 `MaxIdleConns` 和 `MaxOpenConns` 对齐，同时把 `MaxOpenConns` 从 200 调低到 50，再配合内核参数兜底。"

## 二、完整版

### 1. 背景：现象是什么

> "现象是高并发场景下，服务偶发性地连不上 MySQL，报错跟本地端口分配失败有关（类似 `cannot assign requested address`）。这个和卡片一那次 IDSvc FD 堆积不一样——FD 堆积是持续缓慢上涨的慢性病，这次是**在流量突增的时候才会发作**，流量平稳的时候完全正常，是跟并发量直接相关的急性问题。"

### 2. 排查过程：为什么"多出来的连接会被直接关闭"

> "先看 TIME_WAIT 数量和业务报错的时间点，发现完全对得上高并发的时间窗口，所以方向很快锁定在'连接被频繁关闭重建'上，而不是慢性泄漏。
>
> 接着去看连接池的配置，`services/pkg/client/db/db.go` 里 `NewDB` 默认给的 `MaxOpenConns` 是 200，但 `MaxIdleConns` 是固定写死的 100，跟 `MaxOpenConns` 完全没关联。这就是关键——Go 的 `database/sql` 连接池有一个容易被忽略的行为：一个连接用完之后，如果空闲池（受 `MaxIdleConns` 限制）还有空位，就会被留下来复用；但如果空闲池已经满了，这个连接会被**直接物理关闭**，不会等什么超时。
>
> 高并发的时候，同时在用的连接数经常会超过 100（毕竟上限是 200），这些连接用完准备归还的时候，空闲池的 100 个槽位早就被占满了，于是这些'超出 100 的部分'每次用完都会被直接关掉，用的时候又要重新建一条新连接。相当于连接池在高并发下退化成了'伪连接池'——理论上能撑到 200 个连接，但实际上只有 100 个能被真正复用，剩下的每次都是'现开现关'。而主动关闭方是客户端（也就是这个服务自己），大量这种关闭在同一个时间窗口里发生，就集中产生了大量 TIME_WAIT，占满了本地临时端口。"

**机制拆解：手把手过一遍，为什么关闭是"扎堆"发生的**（这一段是整张卡片最容易被追问穿的地方，值得单独拆开讲清楚）

先纠正一个直觉误区：`open`（总连接数）和 `idle`（空闲连接数）不是两个各自涨跌、互相独立的池子，`idle` 其实是 `open` 的一个子集——`open = inUse（正在被用）+ idle（闲着待复用）`。Go 的 `database/sql` 归还一个连接的时候，只走两条路径：**要么有人在排队等，直接转手给它；要么看 idle 池还有没有空位，有就留着，没有就直接物理关闭**（这是源码 `putConnDBLocked` 里的真实逻辑，不是猜的）。

带着这个关系把一次"冲高再回落"过一遍：

| 阶段 | 并发情况 | open（总连接数） | idle（闲置待复用） | 实际发生的动作 |
| --- | --- | --- | --- | --- |
| 平时 | 几十并发 | 几十 | 视归还情况，最多到 100 | 正常复用，不涉及关闭 |
| **冲高** | 瞬间到 150 并发 | 涨到 150——**这里只受 `MaxOpenConns=200` 限制，跟 `MaxIdleConns` 完全没关系** | 趋近 0（几乎全在被用） | 新开的连接直接被下一个请求接过去用，几乎不发生关闭 |
| **回落** | 瞬间掉到个位数 | 从 150 开始下降 | 前 100 个归还的连接：idle 池还没满，**转成 idle**（这部分 open 数不变，因为连接还活着，只是从"在用"变成"闲着"） | 无关闭 |
| **回落（续）** | 同上 | 第 101～150 个归还的连接：idle 池已经满了，**被物理关闭**，`open` 数在这一步才真正下降 | —— | 这 50 次关闭几乎发生在同一两秒内，全部指向 MySQL 的同一个端口 |

关键结论：**"关闭"这个动作，只发生在"idle 池已经满、还有连接要归还"的那一部分连接上**；峰值能冲到多高只受 `MaxOpenConns` 限制，跟 `MaxIdleConns` 无关——所以只要一次突发并发超过了 `MaxIdleConns`，回落的时候，超出 `MaxIdleConns` 的那部分就必然被物理关闭，而且是扎堆关的，不是慢慢关的。每一波"冲高再回落"都会重复这个剧本，产生一波新的 TIME_WAIT，速度超过它自然消失（约 60 秒）的速度，本地端口就被越攒越多的 TIME_WAIT 占满了。


### 3. 根因：一句话总结

> "本质是**连接池的两个容量参数没对齐**：`MaxOpenConns`（能开多少）和 `MaxIdleConns`（能留多少复用）如果不一致，一旦并发量落在这两个数字之间，多出来的连接就会陷入'开了就关、关了又开'的抖动，每一次关闭都是一次主动关闭，高并发下这个抖动的量级足够大，就会把本地端口堆爆。跟卡片一的 IDSvc HTTP 连接池问题是同一个大类（连接生命周期管理没配好），但触发条件不一样——那次是'完全不回收'，这次是'该复用的却被回收了'。"

### 4. 解决方案：三处具体改动

> "一共改了三个地方：
>
> 1. **`services/pkg/client/db/db.go`（`NewDB`）**：`MaxOpenConns` 默认值从 200 降到 50——先把并发上限本身收窄一些；`MaxIdleConns` 不再写死成 100，改成默认对齐 `MaxOpenConns`（如果配置显式指定了 idle 值，就尊重配置），这样空闲池永远够大，不会出现'该复用却被关掉'的情况；另外补上了 `ConnMaxLifetime = 30min` 和 `ConnMaxIdleTime = 2min`，给连接一个正常的生命周期管理，避免连接永远不过期。
> 2. **`services/cmd/idsvc/internal/store/store.go`（`hardenDB`）**：`ConnMaxIdleTime` 从 10 分钟缩短到 2 分钟，`MaxIdleConns` 同样对齐到 `MaxOpenConns`。这里的用意是两头兼顾——高峰期空闲池够大，不会被迫关闭连接产生 TIME_WAIT；低谷期这些连接又能在 2 分钟内自然释放，不会一直占着 MySQL 那边的连接配额不释放。
> 3. **`deploy/kubernetes/helm/copilot/charts/idsvc/values.yaml`**：在 `podSecurityContext.sysctls` 里加了两个内核参数兜底——`net.ipv4.tcp_tw_reuse = 1`，允许 TIME_WAIT 状态的 socket 被复用于新连接；`net.ipv4.ip_local_port_range = "1024 65535"`，把本地可用端口范围从默认的三万多个大幅放大。这两个是防御性的兜底，即使代码层面还有没覆盖到的抖动场景，端口池本身也留了更大的缓冲空间。"

### 5. 效果与复盘

> "改完之后，高并发场景下连接不会再被'该复用却被关闭'，TIME_WAIT 的量级明显下降，端口耗尽的报错也消失了。我自己的复盘是：`MaxOpenConns` 和 `MaxIdleConns` 这两个参数看起来只是简单的两个数字，但它们的关系（idle 是不是够大）比单看某一个数字的绝对值更重要——很多团队会关注'连接数上限设多少合适'，但很少会去检查'空闲池是不是配得下正常并发'，这个刚好是个容易被忽略的隐性联动关系。"

## 三、面试官可能的追问 + 参考答法

**Q1：为什么 `MaxIdleConns` 太小会导致连接被"关闭"，而不是排队等着？**
> "`MaxOpenConns` 和 `MaxIdleConns` 管的是两件不同的事：`MaxOpenConns` 限制的是'同时能开着的连接总数'，如果超过这个数，新请求要排队等；`MaxIdleConns` 限制的是'一个连接用完之后，能不能被留下来给下一次复用'。这两者不冲突也不互相排队——一个连接用完了，`database/sql` 会立刻判断：现在空闲池里的连接数有没有到 `MaxIdleConns` 上限？没到就留着复用，到了就直接关掉。所以'关闭'这个动作发生在连接**归还**的那一刻，跟要不要排队开新连接是两条不同的路径。"

**Q2：这个问题和卡片一的 IDSvc HTTP 连接池碎片化问题，本质上是不是一回事？**
> "大类一样，都是'连接生命周期管理没配好'，但触发的方向正好相反。卡片一是**该关的没关**——每次都新建 Transport，连接只会越攒越多，故障是缓慢的、单向增长的；这次是**该留的没留住**——空闲池太小，明明可以复用的连接被迫关掉，故障是跟并发量强相关的、突发的。一个是'漏水'，一个是'该存的水被倒掉了'，两种都会让人吃亏，但排查的入口不一样：前者看的是连接数是否随流量回落，后者看的是并发量和 idle 配置的关系。"

**Q3：为什么修复里 `MaxOpenConns` 也从 200 降到了 50，只对齐 `MaxIdleConns` 不够吗？**
> "只对齐 idle 确实能解决'该复用却被关闭'这个问题，但 `MaxOpenConns` 单独降低还有另一层考虑：连接数上限本身也是 MySQL 那一侧的资源保护——200 个并发连接对数据库的压力和 50 个是不一样的，尤其是这个服务本身请求量级不需要 200 个并发连接。降低上限、同时把 idle 对齐上限，相当于两件事一起做：一是让池子内部不再抖动，二是给数据库侧也降低了压力，两者不是互相替代，是配合着一起做的。"

**Q4：`tcp_tw_reuse` 和放大端口范围这两个内核参数兜底，是不是意味着代码层面的修复其实没那么必要？**
> "反过来说更准确：这两个内核参数是给代码修复之外的场景留缓冲，不是替代品。就算 idle 和 open 对齐了，正常的连接生命周期管理（`ConnMaxLifetime`、偶尔的连接重建）还是会产生一些 TIME_WAIT，只是量级小了很多。`tcp_tw_reuse` 让这些少量的 TIME_WAIT 端口能被更快复用，放大端口范围让总的可用端口池更大——这是双重防御，代码层面消除了'异常抖动'这个大头，内核参数消化掉'正常但存在'的那部分残留。两者缺一，风险敞口都会变大。"

## 四、讲这张卡片时的几个小提醒

- 这次修复的巧妙之处在于**同时打了两个层次**：代码层（对齐 idle/open 比例）解决根因，内核层（sysctl）兜底防御，讲的时候可以强调"我们不是只改了一个参数，是从应用层到系统层做了双重防御"，体现工程上的完整性思考。
- `MaxOpenConns` vs `MaxIdleConns` 这两个参数的关系是这张卡片的核心考点，一定要能讲清楚"关闭发生在归还连接的那一刻，不是开连接的那一刻"，这是最容易被追问、也最能体现理解深度的一点。
- 结尾呼应卡片一：两次故障都是"连接池参数没配对"，但一个是"完全不回收"、一个是"该留的没留住"，讲完两张卡片正好形成一个对照，说明你对连接池的理解是系统性的，不是背了两个孤立的故事。
