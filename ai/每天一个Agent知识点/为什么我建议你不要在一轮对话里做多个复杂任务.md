# 别把 AI 当微信聊：一篇讲清 Token 膨胀和上下文管理的文章

不知道为什么,我自己用下来总觉得 Claude Code 更省 token,但当时手里其实没什么硬证据。后来越用越觉得这个直觉不像错觉,就专门深入研究了一下这个问题。

研究到最后,我发现背后其实是一个很朴素、但大部分人没意识到的机制:**每一轮对话,AI 都要把这轮之前的全部聊天记录重新读一遍**。

也正因为如此,一个 AI 助手对话刚开始时往往又快又准,聊到后面却会明显变慢、变"迟钝",偶尔还会莫名其妙忘掉你前面强调过的细节,账单涨得也比预期快。

---

## 一、agent loop 的伪代码

AI 模型本身是"无状态"的——它不会自己记住上一轮说了什么。每次你发一条消息,助手实际上是把"从对话开始到现在的所有内容"整包重新发给模型,让它从头读一遍再回答。

```
messages = [ { role: "system", content: SYSTEM_PROMPT } ]

function on_user_turn(user_text):
    messages.append({ role: "user", content: user_text })

    while True:
        # 关键点:每次调用,都是把 messages 这个不断变长的数组整个发出去
        response = call_llm(messages)
        messages.append({ role: "assistant", content: response })

        if response.tool_call is not None:
            result = execute_tool(response.tool_call)
            messages.append({ role: "tool_result", content: result })
            continue   # 还在同一个"用户轮次"里,回头再调一次 LLM
        else:
            break      # 这轮结束,把 response 显示给用户,等下一条输入
```

要点其实是两行加在一起,缺一不可:

```
messages.append(...)             # 内容只增不减,数组越转越长
response = call_llm(messages)    # 但每次调用,发的是整个数组,不是新增的那一点
```

单独看 `messages.append`:很正常,任何对话系统都得记住说过什么,这本身只会让历史**线性**变长,不会平方级增长。

单独看 `call_llm(messages)`:如果它每次只需要处理"新增的那一小块"(类似真正有状态的服务端会话,服务器自己记着之前的内容),历史再长也不会拖累后面每一次调用的成本。

真正让**累计处理量**变成平方级的,是这两件事叠在一起:数组在不断变长(`append`),而每一次调用又要把这个已经变长的数组**整个**重新处理一遍(`call_llm(messages)`)。第 k 次调用要处理的量 ≈ 当时数组的长度 ≈ 前面已经 append 过的总量;把第 1 到第 N 次调用的处理量加起来,就是文章开头那个"平方级增长"的来源。

而且真正在膨胀的粒度,不是"用户看到的轮数",而是"这个 `while` 循环转了多少圈"——只要模型这一步决定调用工具,内层 `while` 就会再转一圈,再调一次 `call_llm(messages)`,而这时 `messages` 已经比上一次调用又长了一截。用户发3句话,内部可能已经调了 7、8 次模型。

## 二、具体对话演示

假设用户依次说了三句话,每句都会触发一次工具调用。用 token 数打个大概比例(数字是示意,不是精确值):

把整个过程拆成一步步的"账本",每一行都是"上一行累计 + 这一步新增",标 🔴 的行就是真正触发 `call_llm()` 的时刻——那一行的"累计"就是这次调用实际要发送、要处理的量:

| 步骤 | 发生的事 | 这一步新增 | messages 累计大小 |
|---|---|---|---|
| 0 | 系统提示词加载 | +200 | 200 |
| 1 | 用户:"帮我看下 utils.py 里的 add 函数是否有 bug" | +50 | 250 |
| 2 | 🔴 调用① `call_llm(messages)` —— 发送 250 | — | 250 |
| 3 | 模型决定调用 `read_file("utils.py")` | +30 | 280 |
| 4 | 工具返回:utils.py 文件内容 | +300 | 580 |
| 5 | 🔴 调用② `call_llm(messages)` —— 发送 580 | — | 580 |
| 6 | 模型给出最终回答:"add 函数没问题" | +100 | 680 |
| 7 | 用户:"顺便把它测试一下" | +20 | 700 |
| 8 | 🔴 调用③ `call_llm(messages)` —— 发送 700 | — | 700 |
| 9 | 模型决定调用 `run_bash("pytest")` | +30 | 730 |
| 10 | 工具返回:测试输出 | +200 | 930 |
| 11 | 🔴 调用④ `call_llm(messages)` —— 发送 930 | — | 930 |
| 12 | 模型给出最终回答:"测试通过" | +80 | 1010 |
| 13 | 用户:"再检查一下 subtract 函数" | +30 | 1040 |
| 14 | 🔴 调用⑤ `call_llm(messages)` —— 发送 1040 | — | 1040 |
| 15 | 模型决定再次调用 `read_file("utils.py")`(同一个文件也要重新读) | +30 | 1070 |
| 16 | 工具返回:文件内容又发一次 | +300 | 1370 |
| 17 | 🔴 调用⑥ `call_llm(messages)` —— 发送 1370 | — | 1370 |
| 18 | 模型给出最终回答:"subtract 函数有个边界条件漏了" | +120 | 1490 |

对着这张表能直接看出两件事:

1. **"累计大小"这一列只会往上涨,从没降过**——这就是 `messages.append` 只增不减的效果,数组从 200 一路涨到 1490。
2. **每个 🔴 行的数字,就是当次 `call_llm` 真正要处理的量**——不是"这一轮新增了多少",而是"到目前为止攒了多少"。

把 6 次调用(🔴 行)实际处理的字数加起来:

```
250 + 580 + 700 + 930 + 1040 + 1370 = 4870
```

用户只说了 3 句话、不到 400 字的"净内容",但因为每一次 `call_llm` 都要重发到当时为止的**全部**历史,6 次调用累计实际处理的字数堆到了 4870——而且能明显看到,**第 15 步甚至重复读了第 4 步已经读过的同一个文件**。历史越长,这种"重复读旧东西"的比例只会越高,累计处理量随轮数近似**平方级**增长。

## 三、小测验:给源代码 vs 给引用,哪个更费 token?

**先看题**

假设你要 AI 帮你检查一个 300 行的函数有没有 bug,有两种问法:

- **问法 A**:把这 300 行代码整段直接贴进你的消息里,问"这段代码有没有 bug"
- **问法 B**:只说"帮我看下 `utils.py` 这个文件",让 AI 自己调用 `read_file` 工具去读这份代码

这一句话本身,两种问法处理的 token 量差不多(A 是直接贴进去,B 是通过工具读进来,代码内容量是一样的)。**但如果接下来你还要在这个对话里接着问 5 件不相关的事,哪种问法会让后面的对话更快堆起来、更难清理?**

(先自己想一下,再往下看分析)

---

**分析**

答案是:**问法 A 更费,而且是"暗亏"——账单上第一时间根本看不出来,要等对话变长以后才会显现出差距。**

区别不在"内容量",而在"这份内容被存在了 `messages` 数组的什么位置":

- **问法 A(直接贴源码)**:这 300 行代码是这条 `user_message` 的正文,跟你的问题文字焊在一起、是同一条消息。以后不管你再问多少件跟它无关的新问题,这 300 行都要跟着这条 `user_message` 一起被反复重发,而且没法被单独摘掉——唯一能清理它的手段是"整体摘要压缩",要等历史逼近上限才会触发,而且一压缩就是有损的。
- **问法 B(给引用,让 AI 自己读)**:同样这 300 行代码,存的是这次 `read_file` 调用产生的 `tool_result`,跟你的问题文字是两条独立的消息。`tool_result` 是"工具产物",不是"你说的话"——可以被单独识别、单独清理:这份内容用完之后,后面不再需要时,可以直接把这条 `tool_result` 从热上下文里删掉或换成占位符,不用动用一次昂贵的摘要调用;真要用的时候,让 AI 重新读一次就行。

一句话总结:**贴源码 = 焊死在对话里,只能等最重的压缩来救;给引用 = 存在一个"随时可丢、按需再取"的位置,清理成本低得多。** 第一次送进去的成本几乎一样,但后面几十轮要不要一直背着它,天差地别。

## 四、真正的解法是压缩,但压缩不是免费的

主流工具的做法是:历史长到接近上限时,自动把早期内容总结成一段摘要,原文舍弃,只留"摘要 + 最近的对话"继续往下走。这是唯一真正通用、能防止历史无限堆叠的手段。

但代价也很实在:

- **有损**——早期对话被压缩成摘要,细节会丢,回头追问细节时模型可能已经想不起来了。
- **会让之前攒的缓存报废**——历史内容整体变了,压缩那一刻之后,下一轮相当于重新全价读一遍新历史,账单会有个小尖峰。
- **压缩本身还要多调一次模型**去做总结,这也要花钱花时间。

## 加餐: 不同 agent 框架怎么对抗 token 膨胀

### 1) pi 和 deepseek-harness 具体怎么做的

如果把实现细节先拨开不看，**pi 和 deepseek-harness 这类框架的做法，说白了就是两件事：前缀省 token + compact。**

1. **前缀省 token**。尽量让 system prompt、工具定义、前面相对稳定的历史吃到缓存；这样后面的每一轮虽然还是会带着旧历史走，但至少前面那一大段不用每次都按原价重算。

   可以举个很具体的例子。假设某一轮真正发给模型的内容长这样:

   ```text
   [system prompt 2000 tokens]
   [工具定义 3000 tokens]
   [前面对话历史 5000 tokens]
   [这一轮新加的用户问题 200 tokens]
   ```

   这一轮总共是 10200 tokens。到了下一轮,如果前面那 10000 tokens 基本没变,只是末尾多了一点新内容,请求就会变成:

   ```text
   [system prompt 2000 tokens]
   [工具定义 3000 tokens]
   [前面对话历史 5000 tokens]
   [上一轮新产生的 tool result / assistant 回复 400 tokens]
   [这一轮又新加的问题 200 tokens]
   ```

   这时候,真正新增的其实只有最后几百 tokens。所谓"前缀省 token",意思不是前面那 10000 tokens 从请求里消失了,而是服务端会发现:"你前面这一大段我上次已经处理过了。" 于是它会直接复用这段前缀的缓存结果,只对最后新增的那几百 tokens 按更高成本重新处理。

   所以你可以把它想成: **历史还是要带着走,但前面那一大坨稳定内容不必每次都重新付全价。**
2. **compact**。当历史越来越长、快接近上下文上限时，就把更早的内容压成摘要，别让整个 `messages` 数组无限膨胀。

pi 基本就是这套思路的一个很典型实现；deepseek-harness 则是在这条路线上把阈值、兜底、输出裁剪这些工程细节做得更细一些。但本质上，它们都还是这套通用框架：**先靠前缀缓存减轻重复读取的成本，再靠 compact 阻止历史无限变长。**

所以这一层并不是 Claude Code 独有优势，而是现在做得比较成熟的 agent 框架都会采用的通用基线。它能让堆叠"没那么快失控"，但还不足以真正解决问题。

### 2) 为什么 Claude Code 看起来更省 token

如果你用过 Claude Code，可能会有一种直觉：**同样是长链路的 agent 任务，它好像没那么容易失控，token 涨得也没那么夸张。**

这里要先说清楚一件事：**前面讲的那两板斧——前缀省 token + compact——Claude Code 其实也一样会做。** 这一层是 pi、deepseek-harness、Claude Code 这类框架都会采用的通用基线，不是 Claude Code 独有。

Claude Code 真正更像是：在这套通用基线之上，又多做了几层**更激进的热上下文瘦身**。也就是说，大家都会想办法复用前面的稳定历史，但 Claude Code 更进一步的地方，是会更积极地把那些已经用完的旧内容从“当前还得反复带着走”的上下文里清出去。

所以这里不用再重复讲第一层了，重点看它比前面两类框架多做了什么。

**Claude Code 更狠的地方：**

1. **旧工具结果会被主动剔除，而不是一直内联重放**。比如早几轮的 `read_file`、`grep`、`bash` 输出，如果已经完成了它的作用，Claude Code 会把这些旧 `tool_result` 从热上下文里删掉或清空，只保留最近几步真正还在工作的结果。这样后面的 ReAct 循环里，增长的主要是“最近工作集”，而不是整个历史一起膨胀。
2. **超大的工具输出不会长期塞在消息里**。很长的文件内容、命令输出、搜索结果，常见做法是落盘或只保留预览；模型真需要时，再用工具重新读取。这样可以避免“同一大段输出在后续十几轮里被反复携带”。
3. **不是一上来就等整体摘要压缩救场，而是先做局部瘦身**。能先删旧 `tool_result`、清空旧输出、裁掉没必要继续携带的内容，就先在这一步做；只有这些还不够时，才触发一次更重的摘要压缩。
4. **它做的不只是“缓存前缀”，而是“保住缓存前缀的同时缩小热上下文”**。这点和很多只靠“前缀缓存 + 超限摘要”的实现相比，体感差异会很明显。

所以，Claude Code 看起来更省 token，本质上不是“它不用重复读历史”，也不是“只有它会做前缀缓存”，而是**它在通用基线之外，更努力地让后续轮次里值得重复读的历史变少**。

换句话说，pi、deepseek-harness 这类框架已经能把问题压住一部分；而 Claude Code 往前又走了一步，把很多本来会在后面十几轮里反复跟着走的旧工具输出，提前从热上下文里清掉了。

不过要注意：这依然只是**把失控推迟、把增速压缓**，不是彻底消灭问题。你要是在同一条对话里硬塞多个互不相干的大任务，哪怕是 Claude Code，最后也还是要面对上下文膨胀、压缩丢细节、缓存失效这些老问题。

## 给使用者的建议

我现在更推荐的方式其实是三步走,而不是像微信聊天一样一句一句往前推:

1. **先用一个会话,把要做什么整体沟通清楚**。任务目标是什么、范围在哪、有哪些约束、最后要交付什么,尽量一次讲明白。
2. **把共识落到文档里**。可以是 plan、todo、需求说明、任务拆解,总之要有一个能承接上下文的文字载体,别把关键信息只留在聊天历史里。
3. **然后 `/clear` ,开一个新会话执行任务**。新会话只围绕这份文档和当前任务往下走,不要再背着前面那一大串沟通过程一起前进。

这样做的好处是:前一个会话负责"想清楚",后一个会话负责"做干净"。既能减少上下文膨胀,也能让模型在执行阶段更聚焦,不容易像长聊天那样越聊越散、越聊越贵。

省着用上下文,才能让它一直保持又快又准——这跟收拾书桌是一个道理:东西堆得越多,找起来越慢,越容易把重要的东西压在底下忘掉。
