Lesson 8 · pi-agent-core

工具执行的权限控制，以及 Skill 和 Tool 的区别

Lesson 1 说过 AgentTool 是「手脚」——能读写文件、跑 shell 命令。这节课拆两件事：手脚被允许做到什么程度谁说了算，以及 Skill（另一个你可能在别处听说过的名字）跟 AgentTool 到底是不是一回事。

Part A · 工具执行的权限控制

1. 问题：模型说"调用它"，就一定会跑吗？

一旦你把一个 AgentTool（比如能执行任意 shell 命令的 bash 工具）注册给 Agent，模型在 assistant 消息里发出一个 toolCall 之后，这条命令是不是就无条件执行了？如果模型决定跑一个危险命令（比如删除一个目录），有没有地方能在真正执行前把它拦下来？

源码里有两层拦截，第一层甚至发生在"要不要问权限"之前：

2. 第一层：没注册的工具，直接查不到

prepareToolCall（agent-loop.ts:600-614）一开始就去 currentContext.tools（Lesson 6 学过的那份快照）里按名字找工具：

const tool = currentContext.tools?.find((t) => t.name === toolCall.name);
if (!tool) {
	return {
		kind: "immediate",
		result: createErrorToolResult(`Tool ${toolCall.name} not found`),
		isError: true,
	};
}

模型只能"看见"并调用 Agent 构造时/运行时注册进 state.tools 的那些工具。没注册 = 模型怎么"想"调用都拿不到——这是最朴素的一层权限控制：不给，就没有。

3. 第二层：注册过的工具，执行前还要过 beforeToolCall

工具存在、参数也校验通过之后，agent-loop.ts:619-646 还有一道关卡：

if (config.beforeToolCall) {
	const beforeResult = await config.beforeToolCall(
		{ assistantMessage, toolCall, args: validatedArgs, context: currentContext },
		signal,
	);
	if (beforeResult?.block) {
		const result = createErrorToolResult(beforeResult.reason || "Tool execution was blocked");
		if (beforeResult.terminate === true) result.terminate = true;
		return { kind: "immediate", result, isError: true };
	}
}

beforeResult.block 是真正的开关：返回 { block: true, reason }，这次工具调用就不会真的执行，runAgentLoop 会直接给模型一条错误结果（内容是 reason），流程照常继续，模型看到"这次被拒绝了"，可能会换个说法再试一次或者放弃。

先猜一猜：pi-agent-core 自带的 bash/edit/read/write 这几个内置工具，有没有内嵌一个"先问用户是否允许"的默认实现？

翻一遍 harness/tools/bash.ts、edit.ts、read.ts、write.ts 就能验证：里面只有路径解析（resolveToolPath）和执行逻辑，没有任何权限判断代码。这跟 Lesson 1 的 streamFn、Lesson 4 的 convertToLlm 是同一个套路——pi-agent-core 只留一个钩子（这里是 beforeToolCall），自己不做任何决策，策略完全交给调用方。

Part B · Skill 和 Tool，是不是同一种东西

4. 问题：Skill 也能被模型"调用"，那它跟 AgentTool 有什么不同？

pi-agent-core 里确实还有一个独立的 Skill 类型（harness/skills.ts、harness/types.ts），从 SKILL.md 文件加载。先别看代码，猜一猜：

Skill 这个接口里，有没有类似 AgentTool.execute() 那样"可以被调用执行"的方法，以及类似 parameters 那样的参数 schema？

Skill 接口的完整定义（harness/types.ts:46-57）：

export interface Skill {
	name: string;
	description: string;
	content: string;        // 完整的技能说明文本
	filePath: string;
	disableModelInvocation?: boolean;
}

对比 AgentTool（types.ts:386-409）：execute() 方法、parameters（JSON Schema）、executionMode（并行/顺序）——这些 Skill 一个都没有。Skill 本质上是一份"内容"，不是一个"可调用的动作"。

5. 模型怎么"知道"有这个 Skill：只看到名字和描述，看不到内容

formatSkillsForSystemPrompt（harness/system-prompt.ts:3-23）把 Skill 列表拼进系统提示词：

<available_skills>
  <skill>
    <name>xxx</name>
    <description>xxx</description>
    <location>/path/to/SKILL.md</location>
  </skill>
</available_skills>

注意只塞了 name/description/filePath（对应上面的 location），完整的 content 根本不在系统提示词里。模型一开始只能看到"有这么一个技能，大概是干什么用的，文件在哪"，跟 AgentTool 需要完整参数 schema 才能被调用完全不是一回事——Skill 更像是留了一个路标，而不是一个能直接触发执行的接口。

6. 真正"用"一个 Skill：把全文塞进上下文，不走工具调用协议

formatSkillInvocation（harness/skills.ts:38-41）：

export function formatSkillInvocation(skill: Skill, additionalInstructions?: string): string {
	const skillBlock = `<skill name="${skill.name}" location="${skill.filePath}">\n...\n${skill.content}\n</skill>`;
	return additionalInstructions ? `${skillBlock}\n\n${additionalInstructions}` : skillBlock;
}

这个函数只是拼一段字符串，把 Skill 的全文包进 <skill>...</skill> 标记里。它不产生 tool_execution_start/tool_execution_end 事件，不经过 beforeToolCall/afterToolCall，因为它压根不在 Lesson 6 讲过的那条"assistant 发 toolCall → prepareToolCall → execute() → tool_execution_* 事件"链路上。谁来决定"现在要注入哪个 Skill 的全文"、以什么形式塞进哪条消息，是调用这个函数的那一层（App/更上层的 harness）自己的事，pi-agent-core 本身不管。

AgentToolSkill
本质一个可执行的函数（execute()）一段文本内容（content）
模型怎么发起assistant 消息里的结构化 toolCall block，带 JSON Schema 校验过的参数没有结构化调用协议；模型先在系统提示词里看到 name/description，真正用上全文靠 App 层调用 formatSkillInvocation 注入
执行事件tool_execution_start/_end，经过 runAgentLoop 的工具调用链路没有对应事件——不是"执行"，是"把一段文本加进上下文"
权限控制点beforeToolCall/afterToolCall 可以 block没有对应的钩子——没有"执行"这个动作，也就没有可拦截的点

这也是 Part A 和 Part B 最终对上的地方：权限控制（beforeToolCall）是专门针对"可执行动作"（AgentTool）设计的机制——Skill 因为根本不经过执行链路，天然就不在这套控制范围内；如果一份 Skill 文本里写了危险指令，防线要靠别的机制（比如它引导模型去调用某个工具，那条工具调用照样会经过 beforeToolCall）。
