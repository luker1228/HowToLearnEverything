Lesson 13 · types.ts + agent-loop.ts

模型的"思考过程"是怎么实现的

你在 UI 里看到模型回复前有一段"思考"文字，会好奇这是不是又发明了一套特殊消息类型、需要单独处理。答案恰恰相反——这节课看它怎么"平凡"地嵌进你已经学过的两套机制（Lesson 4 的消息内容类型、Lesson 1 的流式事件）里，没有另开一条路。

1. 问题：Lesson 1 学过的事件序列里，有没有"思考"的位置？

Lesson 1 讲过一条 assistant 消息流式生成时会发一串 message_start → message_update* → message_end。message_update 具体带什么内容，当时没细看。现在的问题是：如果这条消息里既有"思考文字"又有"最终回答文字"，agent-loop.ts 是不是要单独判断"这段是思考、那段是正文"，分别走两条不同的处理逻辑？

先猜一猜：agent-loop.ts 里处理流式事件的那段 switch，有没有为"思考"单独写一个 case 分支或者一段特殊逻辑？

2. 类型层：ThinkingContent 是第三种内容块，跟文本、工具调用平级

AssistantMessage.content 的类型（@earendil-works/pi-ai 的 types.ts:429）是 (TextContent | ThinkingContent | ToolCall)[]——一条 assistant 消息内部本来就是一个数组，可以按顺序混排"一段思考 + 一段正文 + 一次工具调用"。ThinkingContent（types.ts:356-364）：

export interface ThinkingContent {
	type: "thinking";
	thinking: string;
	thinkingSignature?: string; // provider 特定的不透明回放数据，用于多轮续接
	redacted?: boolean;         // 为真时思考内容被安全过滤器隐去，
	                             // 加密后的原始数据仍保留在 thinkingSignature 里
}

它跟 TextContent（{ type: "text", text }）结构几乎一样，只是换了个 type 标签。从类型系统的角度看，"思考"从来不是一种特殊机制，只是内容数组里又多了一种 type。

3. 流式事件层：三组事件严格对称，agent-loop.ts 一视同仁

流式协议定义在 pi-ai 的 AssistantMessageEvent（types.ts:535-545），text_*、thinking_*、toolcall_* 三组事件结构完全对称：

| { type: "text_start";     contentIndex: number; partial: AssistantMessage }
| { type: "text_delta";     contentIndex: number; delta: string; partial: AssistantMessage }
| { type: "text_end";       contentIndex: number; content: string; partial: AssistantMessage }
| { type: "thinking_start"; contentIndex: number; partial: AssistantMessage }
| { type: "thinking_delta"; contentIndex: number; delta: string; partial: AssistantMessage }
| { type: "thinking_end";   contentIndex: number; content: string; partial: AssistantMessage }
| { type: "toolcall_start"; contentIndex: number; partial: AssistantMessage }
| { type: "toolcall_delta"; contentIndex: number; delta: string; partial: AssistantMessage }
| { type: "toolcall_end";   contentIndex: number; toolCall: ToolCall; partial: AssistantMessage }

agent-loop.ts:326-344 处理这九种事件用的是同一个 case 分支：

case "text_start": case "text_delta": case "text_end":
case "thinking_start": case "thinking_delta": case "thinking_end":
case "toolcall_start": case "toolcall_delta": case "toolcall_end":
	if (partialMessage) {
		partialMessage = event.partial;
		context.messages[context.messages.length - 1] = partialMessage;
		await emit({ type: "message_update", assistantMessageEvent: event, message: { ...partialMessage } });
	}
	break;

这九种事件收到哪一种，都只做同一件事：把 partialMessage 换成 provider 给的最新快照，原样转发成一条 message_update。contentIndex 负责标出这段 delta 属于 content 数组里第几块——真正把碎片拼回完整 ThinkingContent/TextContent 的工作，是 provider 端在构造 partial 时做的，agent-loop.ts 本身不关心、也不需要知道"这一块是不是思考"。

4. 谁按下"开始思考"这个开关

光有类型和事件协议，不代表模型真的会输出 thinking 块——这取决于请求时有没有打开推理。链路是：

Agent._state.thinkingLevel   // "off" | "minimal" | "low" | "medium" | "high" | "xhigh" | "max"（types.ts:300），默认 "off"（agent.ts:77）
  → AgentLoopConfig.reasoning  // "off" 时传 undefined（agent.ts:450）
    → streamFunction(model, llmContext, { ...config, apiKey, signal })  // 整个 config 被展开进 provider 调用的 options（agent-loop.ts:308）

reasoning 具体怎么变成某个 provider 能听懂的参数（比如 Anthropic 的 thinking token 预算），是 pi-ai 内部的事——按 Mission 的范围约定，这一层不展开；只需要知道 ThinkingBudgets（agent.ts 里的 thinkingBudgets 字段）这个"等级 → 具体 token 预算"的映射表也来自 pi-ai，agent 包只负责把用户设置的等级原样传下去。

5. thinkingSignature/redacted 为什么存在：思考不能被随意改写

回想 Lesson 4 讲过 AgentMessage 是贯穿始终的轨迹——如果历史里有一条带 ThinkingContent 的 assistant 消息，下一轮请求要不要原样把它送回去？某些 provider 的多轮推理要求必须原样送回上一轮的思考块，否则推理链条失效；thinkingSignature 就是为这种"必须原样回放"场景准备的不透明凭证，redacted 则处理"思考内容被安全过滤器隐去，但加密后的凭证还留着"这种情况——文字看不到，但回放凭证还能用。这跟 Lesson 5 的压缩形成一个值得留意的张力：文本消息可以被摘要替换，但带 thinkingSignature 的思考块一旦被摘要抹掉，这个凭证也就没了——具体 pi 的压缩逻辑对这类消息是怎么处理的，是下一个值得追问的问题。

回答你的问题

"思考过程"不是单独发明的机制，是已有两套机制上各多长出一个平级分支：内容类型上，ThinkingContent 是 content 数组里跟 TextContent/ToolCall 平级的第三种块；流式协议上，thinking_start/delta/end 是跟 text_*/toolcall_* 结构对称的第三组事件，agent-loop.ts 用同一段代码处理，完全不区分。真正决定"这一轮模型要不要输出思考"的开关是 Agent.thinkingLevel，一路原样传到 provider 调用的 options 里，具体怎么落地是 pi-ai 的事。
