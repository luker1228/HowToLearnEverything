Lesson 5 · pi-agent-core

上下文压缩：轨迹太长了怎么办

兑现 Lesson 4 结尾的彩蛋：harness/compaction/ 内部也调用了 convertToLlm，但用途完全不同——它不是为了喂给主循环，而是为了单独发一次「总结」请求。这节课打开这个模块。

热身回忆：Lesson 4 讲的管道里，把 AgentMessage[] 收窄成 Message[]（LLM 认识的格式）的那个必须实现的函数叫什么？

1. 问题：轨迹只会越涨越长，上下文窗口不会

《深入理解 AI Agent》第二章「为什么需要压缩：不只是长度问题」一节点出一个朴素但容易被忽略的事实：Agent 每执行一次工具调用，轨迹（messages）只会变长，从不自动变短。工具返回的原始结果（一次搜索、一次文件读取）体积往往很大，几次迭代就能把上下文窗口耗尽——书里的实验数据是：不压缩的策略，7 次搜索工具调用就累积了约 36.7 万字符，第 5 次迭代时上下文估算已超过 128K token 上限，直接触发溢出保护，任务失败。

所以压缩不是「锦上添花的优化」，是不做就会硬失败的刚需。但代价也很明确：既然要把历史变短，就必然要修改上下文中间的内容——而 Lesson 里始终没细讲的 KV Cache，恰恰要求前缀不能变。这个张力就是这节课要拆开的东西。

2. 触发时机：什么时候才动手压缩

压缩不是每轮都跑，而是有阈值判断（compaction.ts:247-249）：

export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings): boolean {
	if (!settings.enabled) return false;
	return contextTokens > contextWindow - settings.reserveTokens;
}

默认设置（compaction.ts:158-162）：reserveTokens: 16384（留给「发一次总结请求」本身的开销），keepRecentTokens: 20000（压缩后大致要保留的最近上下文量）。也就是：上下文用量超过「窗口 − 预留额度」才触发，不是窗口刚好用满才触发——这与书里「策略六：自适应窗口化」的「阈值触发」是同一个思路：初期空间充足时不急着压，快顶到上限了再动手。

3. 算法：从后往前找一个安全的切点

findCutPoint（compaction.ts:374-422）的思路是倒着数：从轨迹末尾往前累加每条消息的 token 数，一旦累加到 keepRecentTokens，就在这个位置附近找一个「安全切点」（用户/助手消息的边界，不能切在一次工具调用的中间）——切点之前的全部拿去总结，切点及之后原样保留：

for (let i = endIndex - 1; i >= startIndex; i--) {
	accumulatedTokens += estimateTokens(entries[i].message);
	if (accumulatedTokens >= keepRecentTokens) {
		// 在切点候选里找到 >= i 的最近一个位置作为切点
		...
		break;
	}
}
如果切点刚好落在一次「用户提问 → 助手调用工具 → 工具结果」这个三步交互的中间（比如切在工具结果那一步），会发生什么？

4. 压缩本身也要「发一次请求」——convertToLlm 被复用

这是这节课最值得注意的一点：生成摘要不是本地拼字符串，是单独再发一次 LLM 请求，而这次请求的输入,恰恰是 Lesson 4 那条 convertToLlm 管道的输出（compaction.ts:549，函数 generateSummaryWithUsage 内）：

const llmMessages = convertToLlm(currentMessages);        // AgentMessage[] → Message[]
const conversationText = serializeConversation(llmMessages);
...
const response = await completeSimpleWithRetries(models, model,
	{ systemPrompt: SUMMARIZATION_SYSTEM_PROMPT, messages: summarizationMessages },
	completionOptions, retry, callbacks);

换句话说：convertToLlm 不是「只在主循环发请求前跑一次」的专属逻辑，它是任何需要把 AgentMessage[] 变成模型能读的文本的场景都会复用的一个通用工具函数——压缩模块调用它来准备「要总结的历史」，主循环调用它来准备「要发给模型的正式请求」，两者用的是同一份 harness/messages.ts 里的实现。

另外注意 completeSimpleWithRetries 里一个容易漏看的细节（compaction.ts:110-115）：

const requestOptions: SimpleStreamOptions = {
	...options,
	cacheRetention: "none",   // 总结请求主动放弃写缓存
	sessionId: uuidv7(),      // 用一个全新的 sessionId，不复用主对话的缓存
};

5. 摘要怎么塞回轨迹，以及为什么不会被反复总结

总结文字回来后，被包成一条 compactionSummary 类型的 AgentMessage（messages.ts 的 createCompactionSummaryMessage），插回轨迹，原始的一大段历史被这一条摘要取代。下一次再触发压缩时，compaction.ts:81-85 有一个专门的过滤：

function getMessageFromEntryForCompaction(entry: Entry): AgentMessage | undefined {
	if (entry.type === "compaction") {
		return undefined;   // 已经是摘要的条目，不会再被当成"要总结的原料"
	}
	return getMessageFromEntry(entry);
}

也就是：旧摘要永远不会被"总结的总结"再总结一遍——只有摘要之后新产生的消息，才会在下一次压缩时被拿去跟旧摘要一起生成一份新的、迭代更新的摘要（对应代码里的 previousSummary 参数和 UPDATE_SUMMARIZATION_PROMPT）。

6. 代价：压缩和 KV Cache 到底是不是矛盾的

回到开头的张力。《深入理解 AI Agent》给出的解法是拆开「时机」和「位置」看（第二章「压缩与 KV Cache：看似矛盾，实则互补」）：

压缩不是在单次 API 调用的过程中修改上下文，而是在两次 API 调用之间，由 Agent 框架对消息列表进行预处理：
1. System Prompt 和 Tool Definitions 永远不动——这是最前面的"静态前缀"，KV Cache 持续缓存。
2. 压缩的对象是对话历史——替换位置之后的缓存会失效，但之前的缓存仍然有效。
3. 这是一个有意识的权衡：不压缩，上下文膨胀到超出窗口，任务直接失败；压缩后，虽然损失部分缓存，但上下文长度可控、信息密度更高。

对照代码看这三点全部对上了：shouldCompact 只在接近阈值时才触发（不是每轮都压，减少缓存失效的频次）；压缩只动 messages，从不碰 systemPrompt（静态前缀原封不动）；生成摘要那次请求主动 cacheRetention: "none"，说明这次请求本身也认清了"反正要破坏缓存，不如干脆不指望复用"。

小测验：为什么生成摘要的那次 LLM 请求要主动设置 cacheRetention: "none"，而不是也尝试利用缓存？
