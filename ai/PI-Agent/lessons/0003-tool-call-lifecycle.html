一次工具调用的生命周期

目标：打开上一课故意跳过的黑箱——一个 toolCall 从「模型说要调用」到「变成一条 toolResult 消息」，中间到底经过了几道关卡。

热身回忆：上一课确认过，一个 tool_call（同一个 toolCallId）会不会跨 turn？

1. 书里的框架：事前审批 vs 事后验证

《深入理解 AI Agent》第四章讨论「执行工具」的安全机制时，给出了两种审查时机：

第一种机制是事前审批：在工具执行前，一个模型负责提议行动（Proposer），另一个独立的模型负责审查并批准（Reviewer）……
提议者-审核者机制解决的是「操作执行前审批或操作完成后验证」的问题。

还有一句对理解代码特别关键：

审批失败后不应简单重试，而应将拒绝理由作为工具调用结果加入 Agent 的轨迹……Agent 已经具备处理工具失败的能力，审批机制只是一个新的输入源。

记住这句话——下面看代码时会发现它被原封不动地实现了出来。

2. 对照代码：一次调用要过五道关

agent-loop.ts 里，一个 toolCall 依次经过 prepareToolCall → executePreparedToolCall → finalizeExecutedToolCall 三个函数，可以拆成五道关：

关卡代码位置对应书里的概念
① 找工具currentContext.tools?.find(...)——
② 校验/整理参数prepareToolCallArguments + validateToolArguments参数保真性检查
③ 事前审批config.beforeToolCall（agent-loop.ts:619-647）Proposer-Reviewer「事前审批」
④ 真正执行tool.execute(id, args, signal, onUpdate)骨架里的 Environment.apply()
⑤ 事后验证config.afterToolCall（agent-loop.ts:724-751）Proposer-Reviewer「事后验证」

③ 和 ⑤ 都是可选钩子——不传就直接跳过，工具照常执行。它们的形状不一样，权力也不一样：

  • beforeToolCall 只能二选一：放行，或者 block（附一句 reason）。一旦 block，工具根本不会被执行。
  • afterToolCall 权力更大：工具已经跑完了，但它可以改写结果的 content、details、usage，甚至把 isError 从 false 改成 true——这就是「验证不通过就纠正」。

3. 被拒绝的调用，去哪了？

这里就是书里那句话的实现。beforeToolCall 一旦 block，代码是这么处理的：

if (beforeResult?.block) {
    const result = createErrorToolResult(beforeResult.reason || "Tool execution was blocked");
    return { kind: "immediate", result, isError: true };
    // ↑ 走的是和「工具真正执行失败」完全一样的路径
}

被拒绝的调用不会被特殊处理、也不会中断整个 Agent——它照样变成一条 toolResult 消息（只是 isError: true，内容是拒绝理由），塞进上下文，模型在下一轮会看到这条"失败反馈"，自己决定要不要换个方式重试。这正是"审批拒绝就像一次工具调用失败"——复用同一条反馈通道，不用给 Agent 单独发明一套"被拒绝"的应对逻辑。

小测验 1：beforeToolCall 返回 block: true 之后，这次调用最终会变成塞进上下文的哪一种消息（角色/类型）？
小测验 2：beforeToolCall 对应书里第四章说的「事前审批」还是「事后验证」？

4. 一个彩蛋：工具居然能让整个循环停下

上一课我们说退出路径只有两条——「模型不调工具」和「shouldStopAfterTurn 叫停」。这里要补一个细节：afterToolCall（或工具自己）可以在结果里设置 result.terminate = true。如果这一批工具全都 terminate: true，hasMoreToolCalls 会被强制置为 false——即使模型明明调用了工具，循环也会当成「没有更多工具调用」一样自然停下。

function shouldTerminateToolBatch(finalizedCalls) {
  return finalizedCalls.length > 0 && finalizedCalls.every(f => f.result.terminate === true);
}

典型用法：一个「把控制权交还给用户」或「任务已完成」的工具，执行完之后不希望模型再继续说下去——它可以直接把 terminate: true 写进自己的结果里。严格说，这不是第三条退出路径，而是「模型不调工具」这条路径的一个特殊变体：工具调用发生了，但它的结果让循环表现得像没发生过一样。
