Lesson 6 · pi-agent-core

Agent 类与 agent-loop：状态怎么被更新的

兑现 Lesson 5 结尾的彩蛋：Lesson 1 说过 agent-loop.ts 导出的 runAgentLoop 是不持有状态的纯函数，Agent 类的实例才持有真正的状态——这节课打开这条边界，看这个拆分到底在解决什么问题，以及 Agent 具体怎么把 runAgentLoop 吐出来的事件写进自己的状态。

1. 问题：一份"跑一轮对话"的逻辑，要同时伺候好几个不相关的需求

设想你要从零实现一个 agent 系统。核心逻辑——「给一段历史 + 工具列表，决定要不要调用 LLM、要不要执行工具、什么时候停」——你自然会写成一个函数或一批方法。但很快会发现，这份逻辑还要同时满足另外一堆跟"跑一轮对话"本身毫无关系的需求：

  • UI 要实时看到"助手正在打字"的流式内容，一次性返回结果不够用；
  • 用户可能在等待过程中追加消息，或者中途直接取消；
  • 可能同时有好几个地方（聊天窗口、日志、埋点）都想知道"现在状态变成什么样了"；
  • Lesson 5 里见过：压缩生成摘要要单独发一次请求，复用的是"跑一轮对话"逻辑里的一部分（convertToLlm），但完全不需要背上 UI/订阅/排队这些包袱。

如果把这些需求全塞进同一批方法里，会立刻撞上两个具体的麻烦：核心逻辑没法被单独测试（每次测试都要拉起一整套订阅、排队机制），也没法在"不需要完整 Agent"的场景里被复用（比如 Lesson 5 的摘要请求）。反过来，如果状态更新散落在到处都能改 this._state 的各个方法里，新增一个"我想知道状态变了"的监听点，就得满代码库找哪里动过状态。

pi-agent-core 的解法，是把这份代码切成两个东西，中间只靠一套"事件"通信：

代码实体职责
agent-loop.ts 里的 runAgentLoop只管"这一轮该怎么跑"，不记得之前发生过什么，事情发生就调 emit 吐出去，别的什么都不管
Agent 类的实例接住事件，用 processEvents 方法统一写进自己的状态，再通过 subscribe 广播给所有监听者

这样一来，「runAgentLoop 内部怎么决定跑一轮对话」和「状态怎么被更新、谁能看到更新」变成两个可以分别验证的问题：runAgentLoop 只要保证"同样的输入吐出同样的事件序列"就算对，跟它是不是绑在某个 Agent 实例上无关；Agent 只要保证"每种事件类型都被正确写进状态，且只有这一条路径能改状态"就算对。下面就按这两条主线，对照代码看这套拆分具体怎么落地。

热身回忆：往下看代码之前，先回忆一下——Lesson 1 说 Agent 类用哪个方法把循环发出的每个事件"归约（reduce）"成新的状态？

2. runAgentLoop 这一侧：为什么必须是纯函数

先看 runAgentLoop 这一侧怎么保证"可以单独测试、可以脱离 Agent 复用"。它的签名（agent-loop.ts:95-102）是这样的：

export async function runAgentLoop(
	prompts: AgentMessage[],
	context: AgentContext,       // 只有 systemPrompt / messages / tools 三个字段的快照
	config: AgentLoopConfig,
	emit: AgentEventSink,        // 事件发生时调这个回调，别的什么都不管
	signal: AbortSignal | undefined,
	streamFn: StreamFn,
): Promise<AgentMessage[]>

注意它不接收 Agent 实例，只接收一个 普通数据对象（AgentContext）——这正是"纯函数式"的字面含义：给定同样的输入（prompts、context、config），跑出来的事件序列应该是确定的，跟"这是不是同一个 Agent 实例、之前跑过多少次"完全无关。

这个快照由 Agent 私有方法 createContextSnapshot() 现场生成（agent.ts:437-443）：

private createContextSnapshot(): AgentContext {
	return {
		systemPrompt: this._state.systemPrompt,
		messages: this._state.messages.slice(),   // 浅拷贝，不是原数组引用
		tools: this._state.tools.slice(),
	};
}

.slice() 是关键细节：runAgentLoop 拿到的是当前状态的一份拷贝，而不是指向 Agent 内部数组的引用。runAgentLoop 跑的过程中即使想改，也改不到 Agent 真正的状态——它唯一能"通知"外部发生了什么的方式，是调用 emit。

3. prompt() 调用链：Agent 怎么把快照和回调交给 runAgentLoop

Agent.prompt() 最终落到 runPromptMessages（agent.ts:409-423）：

private async runPromptMessages(messages: AgentMessage[], options = {}): Promise<void> {
	await this.runWithLifecycle(async (signal) => {
		await runAgentLoop(
			messages,
			this.createContextSnapshot(),          // ① 现做一份快照
			this.createLoopConfig(options),         // ② 把配置（包括 convertToLlm）打包
			(event) => this.processEvents(event),   // ③ 把 processEvents 方法当回调传进去
			signal,
			this.streamFunction,
		);
	});
}

三行注释对应三件事：runAgentLoop 需要「看到什么」（快照）、「能用什么规则处理消息/停止」（config）、「发生事情时该调用哪个函数」（emit 回调）。Agent 类把这三样准备好，剩下的全部丢给 runAgentLoop 去跑——这也是为什么 runAgentLoop 可以在完全没有 Agent 实例的场景下被单独测试（agent-loop.test.ts 直接 mock 一个 emit 函数断言事件序列，不需要构造一个 Agent）。

createContextSnapshot() 里 messages: this._state.messages.slice() 用了 .slice() 而不是直接 this._state.messages。如果去掉 .slice()，最可能出什么问题？

4. Agent 这一侧：processEvents 就是字面意义上的 reducer

runAgentLoop 那边解决了"可测试、可复用"，现在看 Agent 那边怎么解决"状态更新路径唯一"。agent.ts:544-591，完整贴出来看比想象中还朴素——就是一个 switch：

private async processEvents(event: AgentEvent): Promise<void> {
	switch (event.type) {
		case "message_start":
			this._state.streamingMessage = event.message;
			break;
		case "message_update":
			this._state.streamingMessage = event.message;
			break;
		case "message_end":
			this._state.streamingMessage = undefined;
			this._state.messages.push(event.message);     // 流式结束才真正落进 messages
			break;
		case "tool_execution_start": {
			const pendingToolCalls = new Set(this._state.pendingToolCalls);
			pendingToolCalls.add(event.toolCallId);
			this._state.pendingToolCalls = pendingToolCalls;
			break;
		}
		case "tool_execution_end": {
			const pendingToolCalls = new Set(this._state.pendingToolCalls);
			pendingToolCalls.delete(event.toolCallId);
			this._state.pendingToolCalls = pendingToolCalls;
			break;
		}
		case "turn_end":
			if (event.message.role === "assistant" && event.message.errorMessage) {
				this._state.errorMessage = event.message.errorMessage;
			}
			break;
		case "agent_end":
			this._state.streamingMessage = undefined;
			break;
	}
	// ...处理完之后，才转发给所有 subscribe() 的监听者（见下一节）
}

几个值得注意的细节：

  • message_start/message_update 只更新 streamingMessage，不动 messages——一条 assistant 消息在流式生成的过程中，UI 看到的是 state.streamingMessage 这个"半成品"，只有 message_end 那一刻才真正 push 进正式的 messages 数组。这解释了为什么 AgentState（types.ts:333-358）要把 streamingMessage 和 messages 设计成两个独立字段——一个是"正在发生"，一个是"已经发生"。
  • pendingToolCalls 每次都新建一个 Set，不是原地 .add()/.delete()——这是不可变更新的写法（immutable update），常见于需要让外部监听者用「引用是否变化」判断"有没有更新"的场景（比如 React 的 useState 心智模型）。
  • 没有对应的 case 就什么都不做——比如 agent_start、turn_start 这两种事件（Lesson 1 事件时序里出现过）在这个 switch 里没有分支，说明它们纯粹是"通知"，不改变 Agent 的任何状态字段。
小测验：turn_end 事件里，processEvents 只在一种情况下才会写 this._state.errorMessage——是什么情况？（提示：看 message 的 role 和某个字段）

5. 顺序：先更新状态，再广播给监听者——不能反

processEvents 最后几行（agent.ts:584-590）：

const signal = this.activeRun?.abortController.signal;
for (const listener of this.listeners) {
	await listener(event, signal);
}

配合 subscribe()（agent.ts:250-253）：

subscribe(listener: (event: AgentEvent, signal: AbortSignal) => Promise<void> | void): () => void {
	this.listeners.add(listener);
	return () => this.listeners.delete(listener);   // 返回一个取消订阅函数
}

关键顺序：switch 分支（状态更新）先跑完，for 循环（广播给监听者）后跑。这意味着 UI 层的监听者收到某个事件时，agent.state 已经是更新之后的最新值——不会出现"UI 拿到 message_end 事件，但 state.messages 里还没有这条消息"的竞态。这也是"多个地方都想知道状态变了"这个诉求（第 1 节列的第三条）真正被满足的地方：不管有几个监听者，它们看到的都是同一个、已经落地的状态。

6. 回头看：第 1 节列的三个诉求，对应上了吗？

代码库本身没有写"为什么"的长篇论证，类注释只有一句话（agent.ts:167-171）：

Stateful wrapper around the low-level agent loop.
Agent owns the current transcript, emits lifecycle events, executes tools, and exposes queueing APIs for steering and follow-up messages.

但把前面几节的代码证据摆在一起，正好对应上第 1 节提出的三个诉求：

第 1 节的诉求代码证据
核心逻辑可以脱离 Agent 单独测试agent-loop.test.ts 直接调 runAgentLoop，传一个 mock 的 emit 函数断言事件序列，完全不需要构造一个 Agent 实例
核心逻辑可以在"没有常驻 Agent"的场景里被复用Lesson 5 见过：harness/compaction/ 生成摘要时复用的是 convertToLlm（同一层的另一个可复用函数）——体现的是同一种设计取向：把可复用的纯逻辑从有状态的外壳里剥离出来
状态更新路径单一、谁都能订阅但改不了状态所有状态变化只能通过 processEvents 这一个 switch 发生，监听者只能"被通知"（subscribe），拿不到能直接改状态的接口

三条诉求，对应的正是「runAgentLoop 是纯函数」（第 2、3 节）+「processEvents 是唯一 reducer」（第 4 节）+「先更新再广播」（第 5 节）这三件事——拆成两层不是为了拆而拆，是这三个具体麻烦逼出来的结构。
