Lesson 4 · pi-agent-core

上下文管道：AgentMessage → Message

目标：打开 Lesson 1 表格里「眼睛」那一格故意留下的悬念——messages 前面「一条处理管线把 App 消息转成 LLM 消息」，到底是哪条管线、为什么需要它。

热身回忆：Lesson 1 的表格里提到，messages 外面还包着「一条处理管线」。这条管线一句话概括，是把什么转成什么？

1. 书里的前提：API 无状态，每次都要重建上下文

《深入理解 AI Agent》第一章说得很直接：

由于模型 API 本身是无状态的，每次调用时都必须由 Agent 框架重新构造足够的上下文。

第二章讨论上下文压缩时，进一步点出这件「重新构造」发生的时机：

压缩不是在单次 API 调用的过程中修改上下文，而是在两次 API 调用之间，由 Agent 框架对消息列表进行预处理。

这两句话合起来，正好是这节课要打开的黑箱：pi-agent-core 里，「两次 API 调用之间，重新构造上下文」具体拆成了哪两步。

2. 代码对照：一条两级管道

官方 README 用一行图总结了这条管道（pi/packages/agent/README.md:58-63）：

AgentMessage[] → transformContext() → AgentMessage[] → convertToLlm() → Message[] → LLM
                    (optional)                           (required)

对应到 agent-loop.ts 的 streamAssistantResponse 函数（每次 LLM 调用前都会跑一次）：

let messages = context.messages;
if (config.transformContext) {
    messages = await config.transformContext(messages, signal);
}
const llmMessages = await config.convertToLlm(messages);
步骤类型变化是否必须典型用途
transformContextAgentMessage[] → AgentMessage[]（形状不变）可选，不传就跳过裁剪旧消息（上下文窗口管理）、注入外部上下文
convertToLlmAgentMessage[] → Message[]（收窄类型）必须，AgentLoopConfig 的必填字段过滤 UI 专用消息、把自定义类型渲染成 LLM 能懂的文本

注意这两步每次 LLM 调用都会重新跑一遍，不是整场对话只跑一次——这正好呼应上面第一章那句话：模型是无状态的，上下文要「每次调用」重建。

3. 为什么需要两种消息：AgentMessage vs LLM Message

README 有一节专门讲这个区分（README.md:47-53）：

The agent works with AgentMessage, a flexible type that can include standard LLM messages (user/assistant/toolResult) and custom app-specific message types via declaration merging. LLMs only understand user、assistant、toolResult。

代码里这个类型只有一行（types.ts:325）：

export type AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages];

Message 来自 @earendil-works/pi-ai——是 LLM API 真正认识的三种角色。CustomAgentMessages 默认是个空接口，靠 TypeScript 的声明合并（declaration merging）让每个 App 往里加自己的类型。harness/messages.ts 就是这么加的（messages.ts:54-61）：

declare module "../types.ts" {
  interface CustomAgentMessages {
    bashExecution: BashExecutionMessage;
    custom: CustomMessage;
    branchSummary: BranchSummaryMessage;
    compactionSummary: CompactionSummaryMessage;
  }
}

换句话说：App/Harness 层需要记住的东西，比 LLM API 能读懂的东西多得多——一次 bash 命令的完整执行记录（给 UI 展示用）、一条压缩摘要标记、一条分支总结——这些在对话轨迹里都是「真实发生过的事」，但没有一个是 LLM API 认识的角色。AgentMessage 就是「App 记住的完整轨迹」，Message 才是「喂给模型这一口能消化的东西」——两者不是一回事，所以中间必须有一层翻译。

小测验 1：Message（LLM 真正认识的类型）一共只有哪几种角色？

4. convertToLlm 不止一个版本——它是契约，不是写死的逻辑

这是这节课最容易被忽略、但很值得注意的一点：convertToLlm 在代码库里至少有两种不同实现，行为并不一样。

实现位置遇到 bashExecution 这类自定义消息怎么办
粗暴版（Agent 类的兜底默认值）agent.ts:33-37 defaultConvertToLlm直接过滤掉——非 user/assistant/toolResult 一律丢弃，不做任何转换
负责版（harness 提供的现成实现）harness/messages.ts:124-168 convertToLlm渲染成文字——bashExecution 变成一条描述执行结果的 user 消息，compactionSummary/branchSummary 包一层 <summary> 标记后也变成 user 消息

两者都符合同一个契约（types.ts:159-160）：不能抛错，遇到处理不了的类型必须给一个安全兜底（通常就是过滤掉），因为「抛错会打断整个循环、发不出正常的事件序列」。至于具体怎么翻译、翻译成什么样，完全由传进来的那个函数决定——AgentLoopConfig.convertToLlm 就是留给每个 App 自己填的一个洞。这正是「区分 AgentMessage 和 Message」换来的好处：核心引擎（agent-loop.ts）永远不需要知道 bashExecution 是什么，它只认「你给我一个能把任意 AgentMessage[] 变成合法 Message[] 的函数」。

5. 用测试钉死执行顺序

agent/test/agent-loop.test.ts:221-272 有一个测试专门验证「先 transformContext 再 convertToLlm」这个顺序：transformContext 把 4 条历史消息裁剪成 2 条（messages.slice(-2)），断言 convertToLlm 收到的就是这裁剪后的 2 条，而不是原始的 4 条。这证明 transformContext 的输出直接是 convertToLlm 的输入——管道是严格串行、单向收窄的，没有反过来的通道。

如果 transformContext 把 10 条 AgentMessage 裁剪成 3 条，convertToLlm 收到的输入是几条？

下一步的彩蛋预告

harness/compaction/ 里的压缩逻辑（compaction.ts:549、809）内部也调用了 convertToLlm——用途不是喂给主循环的 LLM 调用，而是把一段历史先转成 Message[]，再单独发一次 LLM 请求「总结这段历史」，总结完再包成一条 compactionSummary 类型的 AgentMessage 塞回轨迹。这正好是第二章那句话的具体实现：压缩发生在两次 API 调用之间，而不是某次调用内部——下一课我们会打开 harness/compaction/ 看这套机制。
