Lesson 11 · agent-loop.ts

并行执行工具调用：哪一步真并行，哪一步还是顺序

learning-records/0002 已经确立过一条边界：模型只决定"调几个、调哪些工具"，"这一批工具具体怎么跑"是 harness 的决定。但那时只看到了"顺序 vs 并行"这个二选一的结果，没打开"并行"内部到底怎么实现。这节课打开它。

1. 问题：一条 assistant 消息带 3 个 toolCall，是不是从头到尾都同时跑？

如果答案是"是"，那 Lesson 8 讲过的权限确认应该怎么问？三个工具如果都要经过 beforeToolCall 权限检查，同时问三次，用户要在终端里同时回答三个问题吗？这个具体场景就是这节课要拆的第一个矛盾。

先猜一猜：executeToolCallsParallel 里，"找工具 → prepareArguments → validateToolArguments → beforeToolCall 权限检查"这一整套准备工作，对三个 toolCall 是怎么跑的？

2. 真实代码：prepare 排队，execute 才真的并发

executeToolCallsParallel（agent-loop.ts:489-554）先用一个普通 for 循环，逐个 await 每个 toolCall 的准备阶段：

for (const toolCall of toolCalls) {
	await emit({ type: "tool_execution_start", ... });
	const preparation = await prepareToolCall(currentContext, assistantMessage, toolCall, config, signal);
	// ...
	finalizedCalls.push(async () => {
		const executed = await executePreparedToolCall(preparation, signal, emit);
		return finalizeExecutedToolCall(currentContext, assistantMessage, preparation, executed, config, signal);
	});
}

const orderedFinalizedCalls = await Promise.all(
	finalizedCalls.map((entry) => (typeof entry === "function" ? entry() : Promise.resolve(entry))),
);

注意：for 循环里 await prepareToolCall(...) 是真的等——第二个 toolCall 的准备工作，要等第一个准备完才开始。真正被塞进闭包、留到最后 Promise.all 才一起触发的，只有 executePreparedToolCall（调 tool.execute()）这一步。这不是我读代码猜的，types.ts:34-41 的官方注释直接写明白了：

// "parallel": tool calls are prepared sequentially, then allowed tools execute concurrently.
// tool_execution_end is emitted in tool completion order after each tool is finalized,
// while tool-result message artifacts are emitted later in assistant source order.

3. 对上 Lesson 8：这就是权限确认"一个一个问"的原因

beforeToolCall（Lesson 8 讲过的权限钩子）就在这个顺序的准备阶段里面（见 prepareToolCall，agent-loop.ts:600-651）。所以即使这批工具最终会并发执行，权限确认永远是按模型发出 toolCall 的顺序一个一个问的——不存在"三个权限弹窗同时出现"的情况，因为准备阶段本来就没并发。

4. 顺序保证：事件可能乱序，喂给 LLM 的结果不会

三个工具真正并发跑之后，谁先跑完，tool_execution_end 事件就先发出去——这个事件流是按完成时间排的，可能和模型发出 toolCall 的顺序不一样。但最终要塞回 context、喂给下一轮 LLM 的 ToolResultMessage[]，用的是 orderedFinalizedCalls——闭包数组本身保持着 toolCalls 的原始顺序，Promise.all 的返回值天然按输入数组的顺序排列，跟谁先 resolve 无关。所以：UI 上看到的完成顺序可能乱，模型下一轮看到的结果顺序永远和它自己发起调用的顺序一致。

小测验：模型一条消息里按顺序发出 toolCall A、B、C。B 是个很慢的 bash 命令，A、C 很快跑完。喂给下一轮 LLM 的 ToolResultMessage 顺序是？（填三个字母，不加分隔符，如 ABC）

5. 谁能强制走 sequential：目前没有内置工具真的用它

回到 0002 的结论：config.toolExecution === "sequential"（Agent 级别整体配置）或者这一批里任何一个 toolCall 命中的工具 executionMode === "sequential"（工具自己声明），两者任一为真，整批强制顺序（agent-loop.ts:419-425）。但搜一遍 packages/agent/src/harness/tools/ 和 packages/coding-agent/src/core/tools/ 里的内置工具（bash / edit / read / write ...），没有一个真的声明了 executionMode: "sequential"——这个字段目前是留给未来的工具或第三方扩展用的钩子，跟 0006 里 prepareArguments 的情况、Lesson 9 里 AgentHarness.skill() 的情况，是同一种模式的第三次出现：通用的扩展点先造好，具体用不用是另一件事。

回答你的问题

"并行执行"这四个字在 pi 里精确的边界是：准备阶段（找工具、修参数形状、校验、权限审批）永远顺序跑，只有真正的 tool.execute() 才会通过 Promise.all 并发。事件流会按真实完成顺序播报，但最终喂回模型的结果列表始终保持模型原始调用顺序。是否强制整批顺序执行，由 Agent 级别配置或单个工具的 executionMode 声明决定——但目前所有内置工具都没有用后者，"并行"是事实上的默认状态。

本课主参照：pi/packages/agent/src/agent-loop.ts（executeToolCalls:411-426、executeToolCallsSequential:433-487、executeToolCallsParallel:489-554、prepareToolCall:600-651），pi/packages/agent/src/types.ts（ToolExecutionMode:34-42、AgentTool.executionMode:403-409），pi/packages/agent/src/harness/agent-harness.ts:258（toolExecution 配置），pi/packages/coding-agent/src/core/extensions/types.ts:467-473（同一套字段暴露给第三方扩展）。
