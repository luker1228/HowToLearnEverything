Lesson 7 · pi-agent-core

Steering：Agent 正在工作时怎么插入新指令

Lesson 6 引用过 Agent 类头上的注释：「exposes queueing APIs for steering and follow-up messages」——一直没打开这句话。这节课打开它。

1. 问题：Agent 还在跑，你又想加一句话，会发生什么

场景：你让 Agent 修一个 bug，它已经开始读文件、跑工具调用了。这时候你想起来一件事——"顺便也查一下测试文件"——你不想等它把当前这次 prompt() 完全跑完再补。直觉的做法是再调一次 prompt("顺便查一下测试文件")。源码里 prompt() 一开头就检查了这件事（agent.ts:351-354）：

async prompt(input: string | AgentMessage | AgentMessage[], images?: ImageContent[]): Promise<void> {
	if (this.activeRun) {
		throw new Error(
			"Agent is already processing a prompt. Use steer() or followUp() to queue messages, or wait for completion.",
		);
	}
	...
}

直接抛错。这不是 bug，是 Lesson 6 学过的那条规则的自然结果：Agent 同一时间只有一次 runAgentLoop 在跑（activeRun 只有一份），状态更新路径要保持单一，不可能同时接受两组并发的 prompt() 调用互相覆盖对方的状态。错误信息里已经指名了正确的 API：steer() 和 followUp()。这节课看 steer()。

热身：结合 Lesson 6，prompt() 会检查哪个字段来判断"当前是不是已经有一次运行在进行中"？

2. steer() 本身只做一件很小的事：排队

steer()（agent.ts:283-285）：

steer(message: AgentMessage): void {
	this.steeringQueue.enqueue(message);
}

注意它是同步方法，没有 await，也不直接接触 runAgentLoop——它只是把消息塞进 steeringQueue（一个 PendingMessageQueue 实例，agent.ts:125-158），立刻返回。"消息什么时候真正被送进对话"是另一个完全独立的问题，留给下一节。

3. 猜一猜：正在跑的工具调用，会被立刻打断吗？

先别看答案：假设 assistant 这一轮消息里一次性发起了 3 个工具调用（比如同时读 3 个文件），其中一个还没跑完的时候，你调用了 steer()。这条消息会不会立刻插进去，打断那个还在跑的工具调用？

AgentLoopConfig.getSteeringMessages 的文档注释（types.ts:234-241）已经给出了答案：

Returns steering messages to inject into the conversation mid-run.
Called after the current assistant turn finishes executing its tool calls, unless shouldStopAfterTurn exits first.
Use this for "steering" the agent while it's working.

答案是不会。getSteeringMessages 只会在"当前这一轮的 assistant 消息 + 它发起的所有工具调用全部跑完"之后才被调用——具体位置在 agent-loop.ts:259，正好在这一轮的 turn_end 事件发出、shouldStopAfterTurn 检查完之后，下一轮开始之前：

pendingMessages = (await config.getSteeringMessages?.()) || [];

也就是说，steer() 排的队不是"打断"，是"占下一轮开头的位置"。3 个并行工具调用只要有一个还没结束，这一轮就没结束，你的消息就还在队列里等着。

如果 runAgentLoop 一开始（第一轮 assistant 消息还没发出）你就调用了 steer()，这条消息会怎么处理？

4. 排队多条消息，不会一次性全塞进去

PendingMessageQueue.drain()（agent.ts:141-154）：

drain(): AgentMessage[] {
	if (this.mode === "all") {
		const drained = this.messages.slice();
		this.messages = [];
		return drained;
	}

	const first = this.messages[0];
	if (!first) {
		return [];
	}
	this.messages = this.messages.slice(1);
	return [first];
}

默认的 mode 是 "one-at-a-time"（agent.ts:231：new PendingMessageQueue(runtimeOptions.steeringMode ?? "one-at-a-time")）：即使你连续调用三次 steer() 排了三条消息，默认策略下每次轮到 drain() 也只会取出最早的那一条，剩下两条继续留在队列里，会分散在接下来的几轮 turn 里逐条注入——不是一次性全部塞进对话。想要一次性全部注入，要显式把 steeringMode 设成 "all"。

5. steer() 和 followUp()：注入时机不同

followUp()（agent.ts:288-290）的写法跟 steer() 几乎一样——同样只是排队。区别在消费的时机。getFollowUpMessages 的文档注释（types.ts:249-256）：

Returns follow-up messages to process after the agent would otherwise stop.
Called when the agent has no more tool calls and no steering messages.
Use this for follow-up messages that should wait until the agent finishes.
什么时候被 drain效果
steer()当前这一轮工具调用跑完之后，下一轮开始前（agent-loop.ts:259）插进正在进行的运行里，提前影响接下来的走向
followUp()Agent 已经没有更多工具调用、且 steering 队列也空了、本来要停下来的那一刻（agent-loop.ts 里 getFollowUpMessages 调用点，在 inner while 循环退出之后）让 Agent 多跑一轮，而不是打断正在做的事

回到开头的场景："顺便也查一下测试文件"如果是想让 Agent 现在就调整方向，用 steer()；如果是想等它把当前 bug 修完之后再顺带查一下，用 followUp()——两个 API 名字不同，背后对应的是两种完全不同的"什么时候介入"。
