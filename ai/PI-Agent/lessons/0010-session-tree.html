Lesson 10 · coding-agent

Session：多次 run 怎么串成一棵树

Lesson 6-9 一直在讲"一次 prompt() 调用"（也就是聊天里说的 run/trace）内部怎么跑。但一个长任务往往要来回好几条消息才能完成——这些 run 总要被存下来、串起来，还得支持"退回某一步重新说"。这节课打开这层存储结构。

1. 问题：只存一条线够不够？

如果长任务的对话历史只是"消息一条接一条 append 到一个列表里"，会有个具体麻烦：你说错了一句、或者想换个方向重新问，唯一的选择是接着往后说，没法"回到那条消息之前，换一种问法"。真正做到"回退重来"，存储结构就不能是一条线——得能在某个历史节点上分岔出第二条路径，原来那条还留着。这节课看 pi 实际怎么落地这件事。

2. 每条消息只认自己的父节点，不认"这是第几次 run"

coding-agent 里一条持久化消息的基础形状（core/session-manager.ts:46-51）：

export interface SessionEntryBase {
	type: string;
	id: string;
	parentId: string | null;   // 只指向"我的上一条"，不知道自己属于哪次 run
	timestamp: string;
}

注意没有类似 runId 的字段。也就是说，"这些消息属于同一次 run"这件事，在存储层根本没有被显式标记——它是从消息序列里"上一条 assistant 消息结束后，下一条 role === "user" 的消息标志着新的一次 run 开始"这个规律里推出来的一个概念，不是持久化数据自带的字段。

先猜一猜：pi-agent-core 的类型定义里，有没有专门给"一次 run"分配一个 ID、单独记录"这次 run 什么时候开始/结束"的机制？

这跟 Lesson 9 遇到的情况是同一个模式：packages/agent 的 harness/ 目录里，有些东西是"设计好了、类型定义齐全、甚至有单测（reducer.test.ts）"，但产品层 coding-agent 还没接上——所以"一次 run 有没有专属 ID"这个问题，标准答案得看你问的是哪一层。这节课接下来讲的都是真正在用的那一层：coding-agent 自己的 SessionEntry/SessionManager（core/session-manager.ts），不是 packages/agent 里那套暂时用不上的 Record 系统。

3. 树是怎么长出来的：父指针 + 分组

每条 SessionEntry 只存一个 parentId，读回来的时候按父指针分组成一棵树（core/session-manager.ts:159-165）：

export interface SessionTreeNode {
	entry: SessionEntry;
	children: SessionTreeNode[];   // 同一个 parentId 的多条 entry，就是多个分支
	label?: string;
	labelTimestamp?: string;
}

这跟 git 的 commit 图是同一个数据结构套路：每个节点只记"我的上一个是谁"，一个节点有多个"孩子"就意味着从那一点分出了不止一条路径。正常情况下（没人回退重来）每个节点只有一个孩子，整棵树退化成一条线；一旦发生分叉，才会看出"树"这个结构真正派上用场。

4. 分叉具体怎么触发：不是"树里加一个节点"，是开一个新的会话文件

用户层面的入口是 /clone 命令，或者在消息列表里选中一条历史消息回退编辑——两者最终都落到 fork(entryId, options)（agent-session-runtime.ts:262-338）。两种 position 参数对应两种真实场景：

position场景行为
"at"/clone：复制当前整个会话targetLeafId = selectedEntry.id——原地分叉，新会话从当前最后一条消息继续
"before"（默认）选中一条用户消息，想回到它之前重新说targetLeafId = selectedEntry.parentId，并把这条消息原文取出来（extractUserMessageText）塞回输入框——你编辑后重新发送，等于从那个分叉点长出一条新分支

关键细节（agent-session-runtime.ts:288-298）：分叉不是在同一个文件里给树加一个节点，是真的调用 sessionManager.createBranchedSession(targetLeafId) 开一个新的会话文件，这个新文件记着自己的父会话是谁。也就是说，"一棵树"在磁盘上的真实形态，是一组互相记着"父会话是谁"的独立会话文件家族，不是单个文件内部的多分支树——这点跟 packages/agent 那套（未采用的）SessionTree 抽象里"一个 tree 存多个 branch"的设想不完全一样。

小测验：position: "before" 分叉时，新分支的起点 targetLeafId 取的是被选中那条用户消息的哪个字段？

回答你的问题

"完成一个长任务要对话多次"，对应的是一个 Session——由一串 SessionEntry（靠 parentId 互相指认）组成，正常情况下退化成一条线，每次用户发消息触发的一次完整 runAgentLoop 执行就是我们一直说的一次 run（也就是 trace）。但"一次 run"在真正在用的存储层里没有专属 ID，是靠"下一条顶层 user 消息标志新 run 开始"这个模式推出来的隐含边界，不是持久化字段本身；如果想要"退回某一步重新说"，产品给的答案不是在这条线上加个分支节点，而是fork() 出一个全新的、记着父会话是谁的会话文件。
