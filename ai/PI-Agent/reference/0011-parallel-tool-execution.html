并行执行工具调用：真并行 vs 假顺序

配套 Lesson 11。承接参考卡片 3「拆解②」——那张卡讲的是单个 toolCall 内部怎么校验参数，这张卡讲一批 toolCall 之间的执行策略。

调度决策：谁能强制这一批走 sequential

// agent-loop.ts:419-425
const hasSequentialToolCall = toolCalls.some(
  tc => currentContext.tools?.find(t => t.name === tc.name)?.executionMode === "sequential",
);
if (config.toolExecution === "sequential" || hasSequentialToolCall) {
  return executeToolCallsSequential(...);
}
return executeToolCallsParallel(...);

两个开关任一为真，整批（不只是那一个工具）强制顺序：config.toolExecution（Agent 级别整体配置，agent.ts:237 默认值是 "parallel"）或这一批里任何一个 toolCall 命中的工具声明了 executionMode: "sequential"（types.ts:403-409）。目前 packages/agent 和 packages/coding-agent 的内置工具没有一个真的用了后者——是留给未来工具/第三方扩展（coding-agent/core/extensions/types.ts:467-473 同一字段暴露出去）的钩子。

"parallel"内部的真实分工

阶段函数是否并发
找工具 / prepareArguments / validateToolArguments / beforeToolCallprepareToolCall否——for 循环里逐个 await，按 toolCall 原始顺序排队
tool.execute() + afterToolCall塞进闭包，最后 Promise.all是——这才是真正并发的部分

官方注释原文（types.ts:34-41）：「tool calls are prepared sequentially, then allowed tools execute concurrently. tool_execution_end is emitted in tool completion order after each tool is finalized, while tool-result message artifacts are emitted later in assistant source order.」

两种"顺序"不要混淆

顺序依据可能乱序吗
tool_execution_end 事件流真实完成时间会——谁先跑完谁先发
喂回 LLM 的 ToolResultMessage[]模型发出 toolCall 的原始顺序（orderedFinalizedCalls，agent-loop.ts:540-548）不会——Promise.all 按输入数组顺序返回，与 resolve 快慢无关

为什么 prepare 阶段要设计成顺序

直接后果：beforeToolCall（Lesson 8 的权限审批钩子）永远按模型调用顺序一个一个问，不会出现"同一批里三个权限弹窗同时弹出"的情况——因为权限检查就在这个顺序的 prepareToolCall 里面，跟真正耗时的 tool.execute() 是分开的两步。
