Agent 类与 agent-loop：仪表盘怎么接住引擎的事件

配套 Lesson 6。可打印，随时回来查。

调用链全景

Agent.prompt(text)
  → runPromptMessages(messages)
      → createContextSnapshot()          // {systemPrompt, messages, tools} 的浅拷贝
      → createLoopConfig(options)        // 含 convertToLlm / shouldStopAfterTurn 等回调
      → runAgentLoop(messages, snapshot, config, emit=processEvents, signal, streamFn)
          → 引擎内部跑 turn 循环，不断调用 emit(event)
      → processEvents(event) 逐个折进 this._state
      → 广播给 subscribe() 的所有监听者

位置：agent.ts:409-423（runPromptMessages）、437-443（快照）、agent-loop.ts:95-102（runAgentLoop 签名）。

快照：引擎只看数据,不拿 Agent 引用

private createContextSnapshot(): AgentContext {
	return {
		systemPrompt: this._state.systemPrompt,
		messages: this._state.messages.slice(),   // 浅拷贝
		tools: this._state.tools.slice(),
	};
}

runAgentLoop 只接收这个普通对象 + emit 回调，从不持有 Agent 实例——这就是"纯函数式引擎"的字面含义。

processEvents：字面意义上的 reducer

事件状态变化
message_start / message_updatestreamingMessage = event.message（半成品，不进 messages）
message_endstreamingMessage = undefined；messages.push(event.message)（这一刻才真正落地）
tool_execution_start/_end新建一个 Set 增删 pendingToolCalls（不可变更新，不原地改）
turn_end仅当 message.role === "assistant" && message.errorMessage 时写 errorMessage
agent_endstreamingMessage = undefined
agent_start / turn_start无对应 case——纯通知，不改状态

位置：agent.ts:544-591。

顺序：先更新状态，再广播监听者

// processEvents 末尾（agent.ts:584-590）
for (const listener of this.listeners) {
	await listener(event, signal);
}

switch 分支跑完（状态已更新）之后才广播——监听者收到事件时 agent.state 已经是最新值，不会有竞态。subscribe()（agent.ts:250-253）注册监听者，返回取消订阅函数。

为什么拆两层

好处证据
引擎可脱离 Agent 单独测试agent-loop.test.ts 直接调 runAgentLoop + mock emit，不需要构造 Agent
纯逻辑可在无常驻 Agent 场景复用Lesson 5：harness/compaction/ 复用 convertToLlm，同一种"剥离可复用纯逻辑"的取向
状态更新路径单一所有状态变化只经过 processEvents 这一个 switch，没有旁路

类注释（agent.ts:167-171）：「Stateful wrapper around the low-level agent loop. Agent owns the current transcript, emits lifecycle events, executes tools, and exposes queueing APIs...」
