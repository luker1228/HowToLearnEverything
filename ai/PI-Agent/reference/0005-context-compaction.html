上下文压缩：轨迹太长了怎么办

配套 Lesson 5。可打印，随时回来查。

触发阈值

shouldCompact = contextTokens > contextWindow - reserveTokens
设置项默认值含义
reserveTokens16384留给"发一次总结请求"本身的开销
keepRecentTokens20000压缩后大致保留的最近上下文量

位置：compaction.ts:158-162（默认值）、247-249（shouldCompact）。

切点算法

findCutPoint（compaction.ts:374-422）从轨迹末尾往前累加 token，累加到 keepRecentTokens 就在附近找一个"安全切点"——只能切在用户/助手消息边界，不能切在一次工具调用中间。切点之前 → 拿去总结；切点及之后 → 原样保留（retainedTail）。

压缩复用 convertToLlm，但独立发请求

// generateSummaryWithUsage, compaction.ts:549
const llmMessages = convertToLlm(currentMessages);   // 复用 Lesson 4 的管道
const conversationText = serializeConversation(llmMessages);
// ...单独一次 completeSimpleWithRetries 调用，systemPrompt 是总结专用提示词

convertToLlm（来自 harness/messages.ts）不是主循环专属，是任何要把 AgentMessage[] 变成 LLM 可读文本的场景通用复用的函数。

总结请求主动放弃缓存复用（compaction.ts:110-115）：

cacheRetention: "none",  // 一次性请求，缓存这次也没有下次可复用
sessionId: uuidv7(),     // 换新 sessionId，不混用主对话的缓存

摘要塞回轨迹，且不会被重复总结

总结文字包成 compactionSummary 类型的 AgentMessage（createCompactionSummaryMessage），替换掉原始的一段历史。下次压缩时明确跳过已有摘要（compaction.ts:81-85）：

if (entry.type === "compaction") return undefined;  // 摘要不会再被当成"要总结的原料"

只有摘要之后的新消息，才会在下次压缩时跟旧摘要一起生成一份迭代更新的新摘要（previousSummary 参数）。

压缩与 KV Cache：不是矛盾，是权衡

要点说明
静态前缀不动systemPrompt 和工具定义永远不参与压缩，缓存持续有效
缓存失效范围压缩只影响替换位置之后的缓存；之前的仍然有效
权衡不压缩 → 上下文溢出，任务失败；压缩 → 损失部分缓存，但上下文可控、信息密度更高
频次控制只在接近阈值（reserveTokens 留出的余量）时批量触发，不是每轮都压
