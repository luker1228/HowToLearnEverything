关卡代码可选?失败/拒绝时怎么办

这张表讲的是单个 toolCall 内部的五道关。一条 assistant 消息里一批 toolCall 之间怎么调度（顺序 vs 并行、事件顺序和消息顺序为什么会不一样）——见 参考卡片 11。

核心设计原则：拒绝 = 一种工具失败

《深入理解 AI Agent》第四章：「审批失败后不应简单重试，而应将拒绝理由作为工具调用结果加入 Agent 的轨迹」。代码实现：beforeToolCall 的 block 走 createErrorToolResult(reason)，和工具真正抛异常时完全同一条路径——不需要给"被拒绝"单独发明一套处理逻辑，Agent 已经会处理"工具失败"了。

beforeToolCall vs afterToolCall 权力对比

时机能做什么书里叫法
beforeToolCall执行前放行 / 拦截（二选一）事前审批
afterToolCall执行后改写结果的任意字段，包括把成功改判为失败事后验证

拆解②：prepareArguments 与 validateToolArguments 各管什么

层级性质不合格时
prepareArguments单个工具可选的钩子（types.ts:393）纯函数、幂等；只修「意图无歧义但形状不对」的已知情况不处理 → 原样透传，仍要过下一关
validateToolArguments@earendil-works/pi-ai 里每个工具必经的通用校验（packages/ai/src/utils/validation.ts:317）按 TypeBox schema 做类型 Convert/coerce，再严格 Check抛错 → 变成 isError:true 的工具结果，不会被 prepareArguments 绕过

prepareArguments 不是"放宽校验换来的兼容层"，而是在校验之前把已知的错误形状搬正，让校验层永远只认一种当前 schema 期望的标准形状——不需要同时认识历史上所有旧形状。

真实案例（harness/tools/edit.ts:55-77 的 prepareEditArguments）——两类完全不同的动机：

  • 模型序列化怪癖：edits 被传成 JSON 字符串而不是数组 → JSON.parse 还原。
  • schema 版本演进：Edit 工具早期是扁平的单个 {oldText, newText}，后来才升级成批量的 edits[]；旧形状自动搬进 edits 数组。

第二类跟"哪个模型"无关，纯粹是 pi 自己的 schema 改版问题。CHANGELOG.md:372 给出的原始动机正是这一类：「enabling compatibility shims for resumed sessions with outdated tool schemas」——会话恢复时 schema 本身已经改版，而不是"不同模型 API 序列化差异"。外部教程（dg-ai-notes ch05）只讲了第一类，容易让人误以为这个 hook 的设计动机就是"模型差异兼容层"。

设计原则（docs/harness.md:2675）：「AgentTool.prepareArguments is deterministic/idempotent computation... effectful policy belongs in before_tool」——形状修复、硬校验、权限策略是三层不同职责，故意不揉在一起。

这个回调点是通用的，不是 Edit 专属补丁：类型定义在每个工具都有（types.ts:393），甚至暴露给第三方扩展开发者——coding-agent/core/extensions/types.ts:467 的官方注释直接写「Optional compatibility shim to prepare raw tool call arguments before schema validation」。目前整个仓库里唯一真正用它的是 Edit 工具（packages/agent 和 packages/coding-agent 各有一份 prepareEditArguments）。coding-agent 那份的源码注释直接点名了真实模型：「Some models (Opus 4.6, GLM-5.1) send edits as a JSON string instead of an array.」——证实模型序列化怪癖不是假设，是观察到的真实现象。

terminate 彩蛋：工具让循环自然停下

function shouldTerminateToolBatch(finalizedCalls) {
  return finalizedCalls.length > 0 && finalizedCalls.every(f => f.result.terminate === true);
}

这一批工具全部返回 terminate: true → hasMoreToolCalls = false → 循环表现得跟"这轮模型没调用任何工具"一样，自然停下。不是第三条独立退出路径，是「自然停下」这条路径的一个特殊触发方式——见 参考卡片 2 的退出路径表。
