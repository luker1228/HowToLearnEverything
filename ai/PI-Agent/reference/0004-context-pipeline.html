上下文管道：AgentMessage → Message

配套 Lesson 4。可打印，随时回来查。

管道全景

AgentMessage[] → transformContext() → AgentMessage[] → convertToLlm() → Message[] → LLM
                    (可选)                                (必须)
步骤类型变化是否必须典型用途
transformContextAgentMessage[] → AgentMessage[]可选裁剪旧消息、注入外部上下文
convertToLlmAgentMessage[] → Message[]必须过滤 UI 专用消息、渲染自定义类型

每次 LLM 调用（每个 turn）都重新跑一遍这两步——不是整场对话只跑一次。位置：agent-loop.ts 的 streamAssistantResponse。

为什么要分两种消息

是什么LLM 认识吗
Message来自 @earendil-works/pi-ai，只有 user/assistant/toolResult 三种角色✓ 唯一认识的格式
AgentMessageMessage | CustomAgentMessages[keyof CustomAgentMessages]——靠声明合并加自定义类型（bashExecution/custom/branchSummary/compactionSummary……）✗ 只是 App/Harness 自己记的完整轨迹

AgentMessage = App 记住的一切；Message = 喂给模型这一口能消化的东西。两者不是一回事，所以中间必须有翻译层。

常见误解：role 里没有 "system"。系统提示词不是一条消息，是 Context 接口上单独的字符串字段 systemPrompt（packages/ai/src/types.ts:521-522），跟 messages 数组并列，不参与 role 枚举。对应第二章「静态前缀 + 轨迹」结构——systemPrompt 和工具定义是不变的静态前缀，messages 才是随交互增长的轨迹。见 学习记录 0004。

常见误解：应该让 Message（LLM 消息）贯穿始终，不需要 AgentMessage。反例：!!command 这种双感叹号 bash 命令（coding-agent/src/core/messages.ts:29-40）：

interface BashExecutionMessage {
  role: "bashExecution";
  exitCode: number | undefined;
  cancelled: boolean;
  truncated: boolean;
  excludeFromContext?: boolean;  // !! 前缀设的就是这个
}

excludeFromContext 在概念上与 Message 自相矛盾：UserMessage 的语义就是「即将发给 LLM 的一条消息」，没法在这个类型上表达「这条消息发生过，但别发给模型」。convertToLlm 里 excludeFromContext 为真时直接 return undefined——消息留在 AgentMessage[] 轨迹里（UI 能看到完整执行记录），但从未进入过任何一次 LLM 请求。准确的说法应该反过来：AgentMessage 才是贯穿始终的那条轨迹，Message 只是每次发请求前用 convertToLlm 现算出来的临时子集。见 学习记录 0005。

convertToLlm 不止一个版本

实现位置遇到自定义消息类型怎么办
粗暴版（Agent 类默认值）agent.ts defaultConvertToLlm直接丢弃
负责版（harness 现成实现）harness/messages.ts convertToLlm渲染成文字（如 bashExecution → 描述性 user 消息）

共同契约：不能抛错，处理不了就给安全兜底（一般是过滤掉）。具体怎么翻译由传入的函数决定——convertToLlm 是 AgentLoopConfig 里一个可插拔契约，不是写死的逻辑。

执行顺序是严格串行、单向收窄的

test/agent-loop.test.ts:221-272：transformContext 把 4 条消息裁成 2 条，convertToLlm 收到的输入就是这 2 条——不会看到裁剪前的原始消息，也不会有反向通道。
